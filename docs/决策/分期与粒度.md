# 分期与粒度

## 2026-08-28

### v1 做部门粒度，v2 做议会粒度，共享数据模型不共享执行引擎

**决策**：v1 覆盖 10³ 量级的部门（稀疏线性代数），v2 覆盖 10⁷ 量级的个体议会
（数据并行）。两期共用同一份 `Economy` 数据模型，各自有独立的执行引擎。

**Why**：这两个规模在数学对象与性能工程上都是两码事。10³×10³ 的稀疏 Leontief 求解是
毫秒级，GPU 收益有限；10⁷ 个体每轮闭式解是标准的 embarrassingly parallel，适合 SIMD 与 GPU。
在 v1 里提前为 v2 建执行架构是浪费，也是耦合来源。

**How to apply**：不要在 v1 里做 v2 的性能准备。GPU 是 v2 的事。

---

### v1 的地面真相是生产单元集合，不是矩阵

**决策**：`Economy` 的存储是「生产单元的列式数组 + 单元到部门的分组映射」。
v1 恰好每部门一个单元，映射为恒等。投入产出矩阵是从中 group-by 出来的派生视图，不是本体。

**Why**：如果 v1 直接把 A 矩阵、最终需求向量、劳动向量当成地面真相，v2 就不是扩展而是重写。
矩阵里的一行没有「提案」这个概念，而议会是决策主体。

v1 里这层间接是恒等映射，几乎零成本；事后补要重来。

**排除方案**：

- v1 直接用矩阵作为地面真相 — v2 需要重写数据模型，代价远大于 v1 省下的那点间接层

---

### `Technology` 从第一天就是可扩展类型，v1 只实现 Leontief

**决策**：技术表示定义为 enum 或 trait。v1 只实现 `Leontief` 一个变体。

**Why**：部门级技术是 Leontief 固定系数（线性），议会级是可替代的柯布-道格拉斯（非线性）。
两者是不同的数学对象。v1 把「技术等于 A 矩阵」焊死的话，v2 会崩。

代价是 v1 里多十几行，收益是省掉一次重写。

---

### 时间维度从一开始就进数据模型

**决策**：`Economy` 设计成 T 期，T=1 是特例。

**Why**：单期与多期是根本性分叉——多期要求商品带日期、约束跨期、要处理资本存量与生产周期。
从多期退化到单期容易，反过来加是重写。

上游实现完全没有时间维度，这是它最大的简化之一。

## 2026-08-30

### v1 实现 Leontief 与柯布-道格拉斯两个技术变体

**决策**：`Technology` 在 v1 实现两个变体，不是一个。

**Why**：v1 阶段 1 的验收靶子是 dep1ex 冷启动跑出 13 到 14 轮，
而 **dep1ex 的技术是柯布-道格拉斯，不是 Leontief**。

证据在 `research/bench/repro.py:152`：`x = exp(log_b + log_lam − log_p + log_Q)`，
展开是 `x_ij = b_ij · λ_i · Q_i / p_j`——**投入需求依赖投入价格**，
这是柯布-道格拉斯成本最小化的结果。Leontief 的投入需求是 `x_ij = a_ij · Q_i`，与价格无关。
消费侧同理，`d_priv = income · exp / (tot_exp · p)` 是柯布-道格拉斯效用的固定支出份额需求。
这也解释了上游为什么要用 Mathematica 解闭式——Leontief 的需求是平凡的，用不着符号求解。

加这个变体不撑破任何已定决策：`Technology` 本来就是可扩展类型，
固定层固定的是「存在技术这个东西」，不是「技术长什么样」。
**往一个设计成开放的槽位里放第二个选项，正是理论无关在这个字段上的实现方式。**

落地分三处，分属三层：`Technology::CobbDouglas` 这个变体进数据模型；
「给定技术与价格求成本最小化投入需求」进工具箱；
「给定价格这个单元打算产多少」的闭式解是**提案行为，归学者**，
作为 `hahnel_2020_slides` 这个 prefab 的内容，带那篇论文的行为假设。

那个闭式解正是上游用 Mathematica 推导、手工转写、把 `log(p3)` 抄成 `log(p2)` 的
八份表达式之一，所以进来时必须按 [性能架构.md](性能架构.md) 走差分测试。

**参考实现分两块，来自不同文件，别搞混**：柯布-道格拉斯的闭式解与投入需求在
`research/bench/repro.py:149-152`（`num/D` 与 `x` 两个表达式）；
而跑出 13 到 14 轮那个靶子的**调价规则**在 `research/bench/endowment.py` 的
`delta_slides_capv`，由 `confirm.py` 以 `MODE = "slides_capv"` 驱动。

`repro.py` 内联的调价规则是 **2023 论文版**（乘上一轮增量、下限 0.001），
按 [研究/上游代码问题.md](../研究/上游代码问题.md) 那一版 250 轮不收敛。
照它实现协调方法，阶段 1 会跑不出靶子。

**部分收窄**：本条收窄本文 2026-08-28「`Technology` 从第一天就是可扩展类型，
v1 只实现 Leontief」里的 v1 变体数。那条的其余部分——技术表示定义为 enum 或 trait、
理由是两者是不同的数学对象——完全成立，本条正是靠它才成立。

### v1 的规模描述修正为 10³ 到 10⁴ 量级生产单元

**决策**：v1 覆盖的规模从「10³ 量级的部门」改为「10³ 到 10⁴ 量级的生产单元」。

**Why**：dep1ex 是 30,000 个工人议会加 30,000 个消费议会，超出「10³ 部门」这个描述。
但它不构成技术障碍：

本文 2026-08-28 定的地面真相是「生产单元的列式数组加单元到部门的分组映射」，
并注明「v1 恰好每部门一个单元，映射为恒等」。dep1ex 的 30,000 个议会就是 30,000 个生产单元，
按 `industry` 分组——**分组映射不是恒等，而数据模型本来就是按这个设计的**。

执行引擎也跑得动：[性能架构.md](性能架构.md) 实测这个规模单轮 99 毫秒、常驻 54.8 MB，
不需要 v2 的数据并行。

那层间接当初留下的理由是「v2 不用重写」，结果在 v1 内部就兑现了。

**部分收窄**：本条只改本文 2026-08-28 那条决策里的规模措辞，
v1 部门 / v2 议会的分期与「共享数据模型不共享执行引擎」不变。
