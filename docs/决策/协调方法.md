# 协调方法

> 中文「协调方法」对应代码里的 `Procedure`。代码、注释、报错一律英文，中文只用于 `docs/` 与讨论。

## 2026-08-28

### 协调方法由学者提供，内核让出控制权

**决策**：协调方法不由库写死。学者在 Python 层提供自己的实现，库负责调用它。
内核的主循环结构上允许把控制权交出去，不是一次性「数据进、数据出」。

**Why**：库若把机制写死，它就不是基础设施，是一个带几个选项的程序。
机制是学者的研究本身，替他决定等于替他做研究。

这与 [技术选型.md](技术选型.md) 里「Python 接缝开在协调方法这一层」一致：
协调方法一轮调一次、一次运行 10² 次，跨语言开销可以接受；
`Participant` 那一层 v2 是 10⁷ 次，不能开在那里。

实测口径下这个开销可以忽略：协调方法每轮碰的是五组价格向量，
长度 10² 到 10³（见 `research/bench/repro.py:118`），几十 KB。
54.8 MB 是整个经济体，协调方法用不上。跨语言开销占比在 0.1% 量级。

**How to apply**：设计任何扩展点时，先问「这是学者的研究内容，还是重复劳动」。
是研究内容就交出去，是重复劳动就接管。

### 扩展机制是接口，不是算子集

**决策**：库的扩展点是一个协调方法必须满足的接口。
任何满足接口的实现都能用上库的全部周边能力：数据模型、不变量检查、`Evaluator` 指标、
run manifest、参数扫描、确定性种子分发。库不需要把它收进代码库。

**Why**：对照 scikit-learn。第三方实现 `fit` / `predict` / `get_params` / `set_params`
就能直接用 `Pipeline`、`GridSearchCV`、`cross_val_score`，官方文档明写不需要合并进 sklearn。
mesa 同理：用户写 `mesa.Agent` 子类，`step()` 里是任意 Python。
networkx 同理：图数据结构加算法库，新研究就是自己写个吃 `Graph` 的函数。

三个库的共同形态是**基础设施提供周边服务，用户写任意代码，靠接口对接**，
维护者不在关键路径上。反过来，凡是「用预设算子拼装」的库（polars、Keras、PyMC），
维护者都是瓶颈，它们忍受这一点是因为引擎必须看见整个表达式才能做查询优化或自动微分。
本库没有那种回报。

**排除方案**：见 [被否决/协调方法.md](被否决/协调方法.md)

**How to apply**：判断某个能力该不该做成扩展点，问「不做成扩展点会不会把学者堵住」。
会堵住就必须是接口，不能是维护者维护的清单。

### 可比性来自共享的数据模型与评分器，不来自读懂对方的代码

**决策**：两个协调方法可比，判据是它们跑在同一份 `Economy` 上、被同一个 `Evaluator`
按同一套指标打分。库不承诺能读懂学者的实现，也不承诺能判断两个实现是否等价。

**Why**：这是 [插件边界.md](插件边界.md) 里那条可比性负担的正确落点。
sklearn 的两个第三方估计器可比，不是因为 sklearn 能读它们的源码——它读不了——
而是因为它们吃同一个输入、被同一个指标打分。

「能读懂对方写了什么」是可比性之上的另一层能力，需要结构化的方法表示（见被否决记录里的算子方案），
不是可比性的地基。把两者混为一谈会导致为了可比性去做算子，而可比性并不需要它。

**How to apply**：对外描述本库的可比性时，说的是「同一经济体、同一评分器」，
不要说成「可以互相检视对方的方法」——后者 v1 做不到。

### 接口只有一层，`iterate` 是自愿工具

**决策**：协调方法的接口是单一方法：

```
solve(economy, seed) -> Plan
```

三种机制都实现它——迭代调价、劳动时间直接计算、线性规划参照解。

库另外提供一个**自愿使用**的循环工具 `iterate(init, step, converged, max_rounds)`。
学者在 `solve` 里调它，库就拿到轮数、上限保护与发散检测；不调，就只有最终结果。

`iterate` 另收一个可选参数 `plan_of`：给出「本轮状态怎么看成一个计划」，
库据此每轮用**自己**那套量去量，产出跨机制同定义的逐轮轨迹。

`State` 完全不受约束，是学者的任意 Python 对象，库不看里面。

**Why**：定位是工具基础设施，不强迫任何人按某种方式写。提供趁手的工具，
用了觉得好用就自己会用。

排除的两种画法：接口画成两层（外层通用 + 迭代类机制的强制细接口）能让库拿到全部轮数信息，
但学者已有的脚本要拆开循环才接得进来；只有一层且不提供工具，
则 [可复现性.md](可复现性.md) 的收敛轮数基准完全无处可挂。
自愿工具这条路两头兼顾，代价是轮数信息只对用了工具的方法可得。

`plan_of` 买的是**诊断能力，不是可比性**——可比性靠最终配置加过程摘要就够，
见 [不变量与指标.md](不变量与指标.md)「可比性靠原始输出」。

**排除方案**：强制 `record()` 见 [被否决/不变量与指标.md](被否决/不变量与指标.md)

**How to apply**：凡是想让库拿到某种信息，先做成自愿工具。
自愿的参数可以后加而不破坏已有调用，强制的接口不能。

### 提案行为归学者，库提供工具但不写死

**决策**：「给定价格，各部门提出多少产量、要多少投入」这一步属于学者。
库提供 `leontief_demand(economy, prices, targets)` 这类工具摆在那里，
他要换一套自己的提案行为，不调就是了。

**Why**：越俎代庖的是**写死**，不是**提供**。库若把提案行为焊进内核，
等于替学者做了一个理论承诺——上游那八份闭式需求表达式说明提案行为本身就是建模选择。

反过来，库若连 Leontief 需求怎么算都不提供，每个学者重写一遍，
那正是本库要消除的重复劳动。

**How to apply**：这条是「工具原则」的一般形式，适用于所有含理论的计算步骤：
提供，不写死，不设为默认路径。

## 2026-09-05

### 递给学者代码的数组是只读的，`RunSummary` 区分发散与轮数用尽

**决策**：`PriceRule` 收到的三个入参（价格、供需差、相对失衡）都是只读视图，
原地写会抛 `ValueError`；协议文档写明这条约束与它的来源。
`RunSummary` 加 `diverged`，与 `converged` 对称，协调方法没用 `iterate` 时为 `None`。

**Why**：两条都是「静默出错改成当场报错」。

价格规则原地写入参有两条污染路径，实测（合成经济体）：

- 写 `price` — 产量与诚实运行逐位相同，而记录下来的 `indicative_price` 是全零。
  计划归档在一个提案从没用过的价格下
- 写 `imbalance` — **25 轮变 1 轮**，计划整个换了一份，`converged` 仍报 `True`。
  原因是关键字参数按书写顺序求值，`next_price=` 先于 `worst_imbalance=`，
  被改过的失衡决定了收敛判断。轮数正是这个 prefab 对外承诺的东西

`RunSummary` 缺 `diverged` 的后果是：走高层 `run` 的学者拿不到「发散了还是轮数不够」。
这两件事对他的结论意义相反——一个是机制本身的性质，一个是预算给少了。

**排除方案**：递拷贝而不是只读视图 — 有成本，且把原地写这个错误藏起来而不是暴露。

**How to apply**：库递给学者代码的数组，凡是库自己之后还要用的，都递只读视图。

⚠ **2026-09-05 代码对抗审查查出这条只挡住了直接写，两条路径仍然通着**：
写 `arg.base`，以及规则返回一个自己留着、下一轮再写的缓冲区——因为库把返回值按引用
存成了下一轮的价格，那块内存的所有权从来不在库手上。实测：复用缓冲区的规则归档的价格
是 `[902.05, 945.72, 711.81]`，而提案实际用的是 `[899.51, 943.76, 711.26]`；
写 `imbalance.base` 让 25 轮变 1 轮而 `converged` 仍为 `True`。

**递只读视图只保护库自己拥有的那块内存**，而这条 How to apply 当初没有区分「库拥有的」
与「库只是拿着引用的」。正确的做法是**取得所有权再冻结数组本身**（`.base` 为 `None`，
没有洞可钻），而不是冻结一个视图。修复未做，见交接。
