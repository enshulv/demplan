# 可复现性

## 2026-08-28

### 场景必须钉住协调程序的实现本身，不只是名字与参数

（⚠ 适用范围已于 2026-08-28 收窄到库自带的实现，见本文「内容哈希只对库自带的实现算」。
核心洞察——名字与版本号不足以钉住实现——不变。）

**决策**：场景文件引用一个 `Procedure` 时，记录的是它的内容哈希，不只是名字与版本号。
run manifest 里的哈希要能反向定位到具体的实现。
`prefab` 的命名带出处与年份，同一研究的不同算法版本各占一个名字。

**Why**：这条不是从原则推出来的，是从上游那个案例量出来的，
见 [研究/复现记录.md](../研究/复现记录.md)。

上游的已发表结果长期无法被第三方复现。排查后，原因**不是**通常预期的那几样：

| 常见嫌疑 | 实际情况 |
|---|---|
| 参数没公开 | 禀赋 1000 写在论文正文里 |
| 数据没公开 | 四十组输入经济体公开了六年 |
| 随机种子 | 数据是固化的文件，无需种子 |
| 实现有 bug | 有几处，但都不足以造成数量级差异 |

真因是**算法在两次发表之间漂了**，而两份自然语言描述都不足以区分两个版本：
2020 年的会议报告写了一行公式 `w = v(1.05 − 0.5ᵛ)`；
2023 年的论文用一段散文描述了另一条规则。实测下来，前者 14 轮收敛，
后者 250 轮不收敛。两份材料都被当作「同一个算法」引用。

**自然语言不是规格。** 一段描述调价规则的散文，两个称职的实现者会写出两个不收敛性不同的
程序。而这两份材料恰恰是作者为了让他人重实现而发布的。

**排除方案**：

- 只记录 `Procedure` 的名字与语义版本号 — 版本号由人维护，人会忘。
  上游的两个版本从未被赋予不同的名字或版本号，它们在两篇材料里都叫「the price adjustment rule」

**How to apply**：

1. 文档里描述任何算法时，附一份可执行的参考实现，并让文档与实现同源。
   描述与实现分离时，以实现为准
2. `prefab` 不叫 `hahnel_participatory_planning`，叫
   `hahnel_2020_slides` 与 `hahnel_2023_paper`——它们是两个算法，不是一个算法的两个说法
3. 复现文献结果时，把「哪一份材料的哪个版本」当成场景的一部分记下来

### 每条协调程序配一组收敛性回归基准

（⚠ 适用范围已于 2026-08-28 收窄，见本文「收敛轮数基准只对库自带的与使用 `iterate`
的方法成立」。理由与失效模式不变。）

**决策**：每个 `Procedure` 附一组固定输入与期望迭代轮数区间，纳入 CI。
轮数越界时失败。

**Why**：上游那条规则从 2020 版漂到 2023 版，没有任何机制发现。
作者自己在 2026 年提交了两次调价相关的修复，标题分别是
"Fix oscillating behavior" 与 "Fix extremely slow convergence"——
他在手工调参数，而问题在规则本身。一个断言「dep1ex01 冷启动应在 10 到 20 轮之间」
的测试会立刻定位它。

这类基准和 [性能架构.md](性能架构.md) 里的差分测试是互补的：
差分测试保证「算得对」，收敛基准保证「收敛得动」。后者是本领域特有的失效模式——
算式全对、不变量全过，但迭代不收敛，而输出看上去仍然像个经济体。

### 内容哈希只对库自带的实现算

**决策**：库对自己提供的协调方法与 prefab 计算内容哈希，场景引用的名字解析到具体哈希。
对学者自己写的协调方法**不计算哈希**，只在 manifest 里记录他**声明**的出处——
名字、版本、git 提交号、DOI，都可选，取不到就留空并明示「未声明」。

**Why**：对学者的代码，库算的哈希是一个更差的版本控制，理由见
[被否决/不变量与指标.md](被否决/不变量与指标.md)。

而库自带那一半必须保留，因为本条原始决策防的失效模式在库自己身上会重演：
半年后改了 `hahnel_2020_slides` 的实现，旧场景会静默跑出新算法，
名字没变、参数没变、结果变了。那正是上游那个案例的自制版。

**部分收窄**：本条收窄 2026-08-28「场景必须钉住协调程序的实现本身」的适用范围。
那条的核心洞察——名字与版本号不足以钉住实现——完全成立，
只是对学者提供的实现，钉住的责任在他的版本控制那一侧。

---

### 收敛轮数基准只对库自带的与使用 `iterate` 的方法成立

**决策**：轮数区间的 CI 断言适用于库自带的协调方法，以及学者调用了 `iterate` 的方法。
学者自己写循环的方法，库数不出轮数，这条基准对它不适用。

**Why**：接口取了单层加自愿工具（见 [协调方法.md](协调方法.md)），
循环在学者那一侧时库看不见轮数。

**部分收窄**：本条收窄 2026-08-28「每条协调程序配一组收敛性回归基准」的适用范围。
那条的理由——算式全对、不变量全过但迭代不收敛，是本领域特有的失效模式——不变。

### 确定性：声明边界并提供自测工具，不做运行时强制

**决策**：库保证自己那一半逐位可复现——数据加载、指标计算、扫描调度、种子分发。
学者那一半由他负责，库把种子递给他（`solve(economy, seed)`），
并提供 `check_determinism(procedure, economy, seed, n)` 供他自测：跑若干次比对输出，
不一致就报告差在哪。这是工具不是闸门。

**Why**：「确定性」不等于「不许随机」。随机化的协调方法是合法研究，
要保的是给定种子后可复现。

运行时强制做不到也不该做，见 [被否决/不变量与指标.md](被否决/不变量与指标.md)。
只声明不提供工具则学者要等到别人复现失败才发现问题，而那时论文已经发了。

**How to apply**：这条属于「把各种可选检查都提供全」这个方向的一部分，
后续测试工具按同一形态加——提供、可选、显式声明。

## 2026-08-30

### 透明化分三档，prefab 是最高档

**决策**：可比性的关键是让复现者能用同一套工具原样重建。透明化分三档，
库的工作方式是把人往上推：

| 档 | 形态 | 复现者要做什么 |
|---|---|---|
| 低 | 未声明出处 | 做不了。manifest 如实标记这个事实 |
| 中 | 声明了 git 提交号或 DOI | 去找那个仓库、自己装环境、自己对版本 |
| **高** | 已被纳入为 prefab | `pip install` 就有，一行引用即可跑 |

未声明出处时，输出里带一个客观事实标记——「本次运行的协调方法与演化规律未声明出处」。
不拦人、不判词，只记事实，读者自己判断能不能复现。这与
[不变量与指标.md](不变量与指标.md)「差额恒算、命名中性」是同一个模式。

**Why**：透明化不等于库去内省学者的代码——那条已经否决了，
见 [被否决/不变量与指标.md](被否决/不变量与指标.md)。
透明化要的是 manifest 里的出处足以让人找回并重建，两者不冲突。

最高档才真正兑现「用同样的工具原样搭建好」：复现者根本不用去找作者的仓库。
而**「学者一发代码就主动纳入、规整化、复现、做成可用的」这条工作方式，
本质上就是把人从中档推到最高档的机制**——它不只是拉用户，它是透明化的实现手段。

**How to apply**：未声明出处的标记要出现在输出里，不能只在 manifest 深处，
否则读者不会注意到那一格是空的。
