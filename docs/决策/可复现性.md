# 可复现性

## 2026-08-28

### 场景必须钉住协调程序的实现本身，不只是名字与参数

（⚠ 适用范围已于 2026-08-28 收窄到库自带的实现，见本文「内容哈希只对库自带的实现算」。
核心洞察——名字与版本号不足以钉住实现——不变。）

**决策**：场景文件引用一个 `Procedure` 时，记录的是它的内容哈希，不只是名字与版本号。
run manifest 里的哈希要能反向定位到具体的实现。
`prefab` 的命名带出处与年份，同一研究的不同算法版本各占一个名字。

**Why**：这条不是从原则推出来的，是从上游那个案例量出来的，
见 [研究/复现记录.md](../研究/复现记录.md)。

上游的已发表结果长期无法被第三方复现。排查后，原因**不是**通常预期的那几样：

| 常见嫌疑 | 实际情况 |
|---|---|
| 参数没公开 | 禀赋 1000 写在论文正文里 |
| 数据没公开 | 四十组输入经济体公开了六年 |
| 随机种子 | 数据是固化的文件，无需种子 |
| 实现有 bug | 有几处，但都不足以造成数量级差异 |

真因是**算法在两次发表之间漂了**，而两份自然语言描述都不足以区分两个版本：
2020 年的会议报告写了一行公式 `w = v(1.05 − 0.5ᵛ)`；
2023 年的论文用一段散文描述了另一条规则。实测下来，前者 14 轮收敛，
后者 250 轮不收敛。两份材料都被当作「同一个算法」引用。

**自然语言不是规格。** 一段描述调价规则的散文，两个称职的实现者会写出两个不收敛性不同的
程序。而这两份材料恰恰是作者为了让他人重实现而发布的。

**排除方案**：

- 只记录 `Procedure` 的名字与语义版本号 — 版本号由人维护，人会忘。
  上游的两个版本从未被赋予不同的名字或版本号，它们在两篇材料里都叫「the price adjustment rule」

**How to apply**：

1. 文档里描述任何算法时，附一份可执行的参考实现，并让文档与实现同源。
   描述与实现分离时，以实现为准
2. `prefab` 不叫 `hahnel_participatory_planning`，叫
   `hahnel_2020_slides` 与 `hahnel_2023_paper`——它们是两个算法，不是一个算法的两个说法
3. 复现文献结果时，把「哪一份材料的哪个版本」当成场景的一部分记下来

### 每条协调程序配一组收敛性回归基准

（⚠ 适用范围已于 2026-08-28 收窄，见本文「收敛轮数基准只对库自带的与使用 `iterate`
的方法成立」。理由与失效模式不变。）

**决策**：每个 `Procedure` 附一组固定输入与期望迭代轮数区间，纳入 CI。
轮数越界时失败。

**Why**：上游那条规则从 2020 版漂到 2023 版，没有任何机制发现。
作者自己在 2026 年提交了两次调价相关的修复，标题分别是
"Fix oscillating behavior" 与 "Fix extremely slow convergence"——
他在手工调参数，而问题在规则本身。一个断言「dep1ex01 冷启动应在 10 到 20 轮之间」
的测试会立刻定位它。

这类基准和 [性能架构.md](性能架构.md) 里的差分测试是互补的：
差分测试保证「算得对」，收敛基准保证「收敛得动」。后者是本领域特有的失效模式——
算式全对、不变量全过，但迭代不收敛，而输出看上去仍然像个经济体。

---

### 内容哈希只对库自带的实现算

**决策**：库对自己提供的协调方法与 prefab 计算内容哈希，场景引用的名字解析到具体哈希。
对学者自己写的协调方法**不计算哈希**，只在 manifest 里记录他**声明**的出处——
名字、版本、git 提交号、DOI，都可选，取不到就留空并明示「未声明」。

**Why**：对学者的代码，库算的哈希是一个更差的版本控制，理由见
[被否决/不变量与指标.md](被否决/不变量与指标.md)。

而库自带那一半必须保留，因为本条原始决策防的失效模式在库自己身上会重演：
半年后改了 `hahnel_2020_slides` 的实现，旧场景会静默跑出新算法，
名字没变、参数没变、结果变了。那正是上游那个案例的自制版。

**部分收窄**：本条收窄 2026-08-28「场景必须钉住协调程序的实现本身」的适用范围。
那条的核心洞察——名字与版本号不足以钉住实现——完全成立，
只是对学者提供的实现，钉住的责任在他的版本控制那一侧。

---

### 收敛轮数基准只对库自带的与使用 `iterate` 的方法成立

**决策**：轮数区间的 CI 断言适用于库自带的协调方法，以及学者调用了 `iterate` 的方法。
学者自己写循环的方法，库数不出轮数，这条基准对它不适用。

**Why**：接口取了单层加自愿工具（见 [协调方法.md](协调方法.md)），
循环在学者那一侧时库看不见轮数。

**部分收窄**：本条收窄 2026-08-28「每条协调程序配一组收敛性回归基准」的适用范围。
那条的理由——算式全对、不变量全过但迭代不收敛，是本领域特有的失效模式——不变。

---

### 确定性：声明边界并提供自测工具，不做运行时强制

**决策**：库保证自己那一半逐位可复现——数据加载、指标计算、扫描调度、种子分发。
学者那一半由他负责，库把种子递给他（`solve(economy, seed)`），
并提供 `check_determinism(procedure, economy, seed, n)` 供他自测：跑若干次比对输出，
不一致就报告差在哪。这是工具不是闸门。

**Why**：「确定性」不等于「不许随机」。随机化的协调方法是合法研究，
要保的是给定种子后可复现。

运行时强制做不到也不该做，见 [被否决/不变量与指标.md](被否决/不变量与指标.md)。
只声明不提供工具则学者要等到别人复现失败才发现问题，而那时论文已经发了。

**How to apply**：这条属于「把各种可选检查都提供全」这个方向的一部分，
后续测试工具按同一形态加——提供、可选、显式声明。

## 2026-08-30

### 透明化分三档，prefab 是最高档

**决策**：可比性的关键是让复现者能用同一套工具原样重建。透明化分三档，
库的工作方式是把人往上推：

| 档 | 形态 | 复现者要做什么 |
|---|---|---|
| 低 | 未声明出处 | 做不了。manifest 如实标记这个事实 |
| 中 | 声明了 git 提交号或 DOI | 去找那个仓库、自己装环境、自己对版本 |
| **高** | 已被纳入为 prefab | `pip install` 就有，一行引用即可跑 |

未声明出处时，输出里带一个客观事实标记——「本次运行的协调方法与演化规律未声明出处」。
不拦人、不判词，只记事实，读者自己判断能不能复现。这与
[不变量与指标.md](不变量与指标.md)「差额恒算、命名中性」是同一个模式。

**Why**：透明化不等于库去内省学者的代码——那条已经否决了，
见 [被否决/不变量与指标.md](被否决/不变量与指标.md)。
透明化要的是 manifest 里的出处足以让人找回并重建，两者不冲突。

最高档才真正兑现「用同样的工具原样搭建好」：复现者根本不用去找作者的仓库。
而**「学者一发代码就主动纳入、规整化、复现、做成可用的」这条工作方式，
本质上就是把人从中档推到最高档的机制**——它不只是拉用户，它是透明化的实现手段。

**How to apply**：未声明出处的标记要出现在输出里，不能只在 manifest 深处，
否则读者不会注意到那一格是空的。

## 2026-09-05

### seed 是 64 位无符号整数，派生用 SplitMix64

**决策**：`solve(economy, seed)` 的 `seed` 是 0 到 2⁶⁴−1 的整数。
`split_seed(seed, n)` 用 SplitMix64 生成 n 个子种子。
`rng(seed)` 返回 `numpy.random.default_rng(seed)`。

**Why**：SplitMix64 有公开规范，跨语言可逐位复现，扫描调度在 Rust 侧派生种子时
与 Python 侧算出的相同。

## 2026-09-05

### 设定文档是输入，不只是记录；与 run manifest 分开两份

**决策**：库产出一份**运行设定文档**：跑完吐出来，复现者喂回去就得到同一套设定。
它与 run manifest 是**两份**——设定文档装设定（可加载），manifest 装溯源（只读），
设定文档的哈希进 manifest。

**Why**：现有决策讲的 manifest 全是记录方向的——记下来给人看、给人事后查。
**只有可加载的那一半能卸掉重配置负担**：复现者不必逐条手动核对、手动配置。

这件事的价值不止于复现。**重配置负担是可选性的主要成本**——把它卸掉，
以后每一处「要不要做成可选」的判断都变便宜。所以这份文档是承重的，不是配角。

分成两份是因为一份要能分辨「哪些字段是设定、哪些是这次跑出来的结果」，
否则喂回去会把上次的结果当输入。

**这份文档能承诺什么，不能承诺什么**：库拥有的部分自动复原（声明的层、
库自带 procedure 的内容哈希、参数、种子、加载器与其参数、库版本）；
学者拥有的代码照本文「内容哈希只对库自带的实现算」办——不哈希，
只记他声明的出处，取不到就留空并**明示「未声明」**。

**排除方案**：设定与溯源合成一份 — 加载时要分辨哪半是输入，边界模糊。

---

### 设定文档的版本规则：缺键用默认值，未知键报错，已删除的键明确报错

**决策**：

| 情况 | 行为 |
|---|---|
| 文档有键、库认识 | 用它 |
| 文档缺键、库有该键 | **用默认值，不报错**（旧文档喂新库要能跑） |
| 文档有键、库不认识 | **报错**，且要分清两种成因 |

第三种的两个成因**报错文案必须不同**：库比文档旧（文档来自更新的版本）→「这份文档需要更新的库」；
库比文档新且该键**已被删除** →「这个设定在本版本已不存在」，并说清何时删的、为什么。
后者要求库留一份**已退役键的登记表**（键名、删除的版本、理由），没有它删除会退化成通用报错。

**还有一条约束**：**新增的键，默认值必须保持旧行为。** 否则旧文档喂进新库虽然不报错，
跑出来却是另一套设定——名字没变、参数没变、结果变了，正是本文这一族决策防的那个形状。
**做不到行为保持默认值的新特性，就不能悄悄加**，要走显式的版本变更。

**Why**：可加载这件事一旦做了，「静默忽略一个新键 = 用旧语义跑新配置」就从不可能变成很容易。

---

### `Economy` 算内容哈希，逐字节，另存逐列哈希

**决策**：库给 `Economy` 算一份内容哈希写进设定文档，**逐字节，不降精度**。
除整体哈希外**另存逐列哈希**，不匹配时报错要说清是哪一列不同。
哈希算法带版本标识（旧文档据此仍可解读）。

**Why**：经济体对不上时，复现者手里是**同一份代码配不同的数字**，任何地方都看不出差别。
这正是本文开头那个案例的形状：上游已发表结果长期无法复现，而参数与数据都是公开的，
失效在「拿到的和当初那份不是同一份而没人发现」。

它覆盖「加载器名 + 参数」覆盖不到的三类：手搭的经济体、学者自己写的加载器、
**以及加载器自己漂移**（参数一样、加载器换了版本）。最后一类在本仓有先例：
`research/bench/repro.py` 的 `parse` 会静默截断长度不一致的投入记录，而 Rust 加载器对同样输入报错。

选逐字节是为学术可用性——降精度会吞掉真的小差异，而本库的收敛判据是 3% 到 5% 的阈值，
末位差异确实可能改变轮数（阈值穿越）。代价是跨平台的浮点末位差异会被报成「不是同一个经济体」，
**逐列哈希就是为了让这种警报可诊断**：报「`input_coefficient` 这一列不同，其余相同」，
学者一眼能判断是加载器差异还是真换了数据。

成本实测：dep1ex01 的经济体 53.3 MB，sha256 耗时 0.064 秒，对照一次求解 1.2 秒可忽略。

**这条不适用于代码。** 本文「内容哈希只对库自带的实现算」的理由是「对学者的代码，
库算的哈希是一个更差的版本控制」——那条对代码成立（代码有 git），
对一份内存里的数组不成立，那些数组没有任何版本控制。

**How to apply**：哈希相同只证明**数组逐位相同**，不证明同一个库版本、numpy、平台或求解器。
文档里这一格宣称什么，必须精确等于它检查什么。

**排除方案**：降精度后哈希 — 吞掉可能改变轮数的差异；
只记来源与参数不算哈希 — 手搭经济体与加载器漂移都发现不了。

### 设定文档的具体形状：JSON、独立函数、按列哈希

**决策**：把 2026-09-05「设定文档是输入」那条落成可施工的规格。以下每一项都是本条新定的。

**格式**：JSON，UTF-8，`sort_keys=True`，缩进 2。
**排除**：TOML — 写入端要额外依赖；YAML — 要依赖，且隐式类型转换会把 `no` 读成布尔。

**API 是独立函数，不焊进 `run`**：

```
run_configuration(procedure, economy, seed, loader=None, plan=None) -> RunConfiguration
RunConfiguration.to_json(path) / RunConfiguration.from_json(path)
```

`run()` 的签名与 `RunResult` 不变。**Why**：`run` 的职责是跑。设定文档要算经济体的内容哈希
（dep1ex01 是 53.3 MB、0.064 秒），焊进 `run` 就等于每次跑都付这笔钱，
而参数扫描要跑上千次。学者显式调用，付不付由他定。

**顶层键**：`configuration_version`(int)、`library_version`、`seed`、
`economy`、`procedure`、`loader`、`plan_fields_absent`。

`plan_fields_absent` 取自 `plan.absent_fields`；不给 `plan` 就是 `null`，
与加载器块同样的「未声明」形式。**这个函数只对 `plan` 做鸭子类型**，
不导入 `Plan`——设定文档记的是学者声明了什么，不是去验证他的计划。

**经济体哈希块**：`{"algorithm": "sha256-columns-v1", "digest": hex, "columns": {列名: hex}}`。
规范化钉死如下，换任何一步都要改 `algorithm` 的版本号：

- 每列先 `np.ascontiguousarray`，再规范成小端（`astype(dtype.newbyteorder("<"), copy=False)`），
  然后把 `列名   dtype.str   shape   tobytes()` 喂 sha256
- `extra` 袋的键一并作为列，列名带前缀 `commodity_extra.`、`unit_extra.`、`consumer_extra.`
- 整体 `digest` 是把列名排序后各列的十六进制摘要依次拼接，再 sha256

**规范成小端而不是拒收大端平台**：代价是一次拷贝，换来的是跨平台可比。

**协调方法块**：库自带的（`type(procedure).__module__` 以 `cyberstride.` 开头）记
`{"kind": "library", "module", "qualname", "source_digest", "parameters"}`，
`source_digest` 是**定义它的模块源文件的字节**的 sha256——不是类的源码，
因为模块级常量（如 `PRICE_STEP_CEILING`）同样决定行为。
学者的记 `{"kind": "researcher", "declared_origin": null}`，
**键恒在、值为 `null` 就是「未声明」的明示形式**，不是把键省掉。

**参数**：协调方法是数据类时记它的字段；JSON 标量直接记，其余（可调用、数组）按上一段
同样的「库自带／学者」两分法记。不是数据类时 `"parameters": null`。

**加载器块由学者显式给**，不给就是 `null`。**Why**：`Economy` 是固定层，
给它加一个来源字段等于往固定层塞溯源数据。经济体的身份由内容哈希钉住，加载器块只是便利。

**版本规则的实现**：退役键登记表是模块级的
`RETIRED_KEYS: dict[str, RetiredKey]`，`RetiredKey` 带 `removed_in` 与 `reason`。
v1 是空的，但机制要有并且要有测试。

**「新增键的默认值必须保持旧行为」怎么落到测试上**：一条测试把当前全部默认值 dump 成 JSON，
与一份入库的基准比对。改了默认值就转红，逼人显式面对。

**How to apply**：这些是可施工的形状，不是新的纲领。与上面几条冲突时以上面几条为准。

### 学者写的协调方法也记参数；设定文档的六处施工细节定案

**决策**：**学者块也带 `parameters`**，走与库自带块完全相同的一套规则
（数据类记字段、JSON 标量直记、非标量套库／学者两分法、非数据类记 `null`）。
`declared_origin` 与「不给学者的代码算 `source_digest`」两条不变。

**Why**：原来把学者块钉成恰好 `{"kind", "declared_origin"}` 两个键，
是把「不给学者的代码算内容哈希」错误地延伸到了「不记他的参数」。
那条的理由是「对学者的代码，库算的哈希是一个更差的版本控制」——
**那对代码成立，对参数不成立**：参数是数据不是代码，
库对学者的数据类和对自己的数据类一样能自省。

后果正好打在本库的目标用户上。**学者自己写的协调方法是最常见的情况**，
参数记不下来，「跑完吐出来、喂回去就得到同一套设定」这条对他就不成立——
而按 [纲领定位.md](纲领定位.md) 2026-09-05，让领域里的下一个人更快开始工作是排优先级的判据。

**部分覆盖**：本条推翻同日
[设定文档的具体形状](#设定文档的具体形状json独立函数按列哈希)
里「学者的记 `{"kind": "researcher", "declared_origin": null}`」这一句的**穷尽性**。
不哈希学者代码、只记声明的出处两条不变。

**另外六处定案**：

1. **顶层键是 8 个**，`core_version` 与 `library_version` 并列。原清单漏了它。
2. **列头的字节编码钉死**：`f"{name}
{dtype.str}

**一条选定的代价**：`plan_fields_absent` 记的是学者声明的字段名，
**库不校验它们是不是 `Plan` 真有的字段**——这是「只做鸭子类型、不导入 `Plan`」的直接后果。
字段名写错一个字会原样进档而没有任何东西转红。这是选定的代价，不是缺陷，
但要写在学者读得到的地方。
