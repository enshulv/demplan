# 可复现性

## 2026-08-28

### 场景必须钉住协调程序的实现本身，不只是名字与参数

**决策**：场景文件引用一个 `Procedure` 时，记录的是它的内容哈希，不只是名字与版本号。
run manifest 里的哈希要能反向定位到具体的实现。
`prefab` 的命名带出处与年份，同一研究的不同算法版本各占一个名字。

**Why**：这条不是从原则推出来的，是从上游那个案例量出来的，
见 [研究/复现记录.md](../研究/复现记录.md)。

上游的已发表结果长期无法被第三方复现。排查后，原因**不是**通常预期的那几样：

| 常见嫌疑 | 实际情况 |
|---|---|
| 参数没公开 | 禀赋 1000 写在论文正文里 |
| 数据没公开 | 四十组输入经济体公开了六年 |
| 随机种子 | 数据是固化的文件，无需种子 |
| 实现有 bug | 有几处，但都不足以造成数量级差异 |

真因是**算法在两次发表之间漂了**，而两份自然语言描述都不足以区分两个版本：
2020 年的会议报告写了一行公式 `w = v(1.05 − 0.5ᵛ)`；
2023 年的论文用一段散文描述了另一条规则。实测下来，前者 14 轮收敛，
后者 250 轮不收敛。两份材料都被当作「同一个算法」引用。

**自然语言不是规格。** 一段描述调价规则的散文，两个称职的实现者会写出两个不收敛性不同的
程序。而这两份材料恰恰是作者为了让他人重实现而发布的。

**排除方案**：

- 只记录 `Procedure` 的名字与语义版本号 — 版本号由人维护，人会忘。
  上游的两个版本从未被赋予不同的名字或版本号，它们在两篇材料里都叫「the price adjustment rule」

**How to apply**：

1. 文档里描述任何算法时，附一份可执行的参考实现，并让文档与实现同源。
   描述与实现分离时，以实现为准
2. `prefab` 不叫 `hahnel_participatory_planning`，叫
   `hahnel_2020_slides` 与 `hahnel_2023_paper`——它们是两个算法，不是一个算法的两个说法
3. 复现文献结果时，把「哪一份材料的哪个版本」当成场景的一部分记下来

---

### 每条协调程序配一组收敛性回归基准

**决策**：每个 `Procedure` 附一组固定输入与期望迭代轮数区间，纳入 CI。
轮数越界时失败。

**Why**：上游那条规则从 2020 版漂到 2023 版，没有任何机制发现。
作者自己在 2026 年提交了两次调价相关的修复，标题分别是
"Fix oscillating behavior" 与 "Fix extremely slow convergence"——
他在手工调参数，而问题在规则本身。一个断言「dep1ex01 冷启动应在 10 到 20 轮之间」
的测试会立刻定位它。

这类基准和 [性能架构.md](性能架构.md) 里的差分测试是互补的：
差分测试保证「算得对」，收敛基准保证「收敛得动」。后者是本领域特有的失效模式——
算式全对、不变量全过，但迭代不收敛，而输出看上去仍然像个经济体。
