# 性能架构

## 2026-08-28

### 整个经济体常驻内存，一轮迭代不碰磁盘

**决策**：`Economy` 全部驻留内存，采用列式 f64 数组。只在 run 开始时读磁盘、结束时写。

**Why**：这条是从上游实现的实测教训来的，详见 [研究/复现记录.md](../研究/复现记录.md)。

上游把数据放进 SQLite，每轮迭代对 600 万行做带关联子查询的 UPDATE，
同规模一次实验约 4 小时。同样的计算用列式数组做，实测单轮 99 毫秒、
全经济体常驻内存 54.8 MB，100 轮不到 10 秒。差约 1450 倍。

上游走到磁盘上的原因是 4 GB JVM 堆被撑爆。但撑爆的不是数据量，是表示方式——
嵌套 map 加 keyword 相对裸数组有 50 到 100 倍开销。这是「表示方式导致的内存墙」，
用「把数据挪到磁盘」来解决，代价是慢三个数量级。

**排除方案**：

- 用数据库当计算基质 — 见 [被否决/性能架构.md](被否决/性能架构.md)

**How to apply**：v2 要算内存账。10⁷ 议会 × 100 商品 × 8 字节 = 每个字段 8 GB，
加上指数、需求、暂存数组是 30 到 40 GB。所以 v2 必须走稀疏表示，不能沿用 v1 的稠密布局。

---

### v1 的性能目标是多 run 吞吐，不是单 run 速度

**决策**：v1 的性能工程瞄准大量小任务的吞吐——run 之间零残留状态、setup 便宜、
无每 run 的分配风暴、场景级并行、结果流式落盘。

**Why**：10³ 部门的稀疏 (I−A)x=d 一次解是毫秒级，跑 100 轮迭代仍在一秒以内。
v1 没有单次运行的性能问题。

吃算力的是运行次数：参数扫描、蒙特卡洛、敏感性分析。学者要的图上，
横轴每一个点都是一次完整运行。

---

### 每个优化过的内核保留一份参考实现，并有差分测试

**决策**：任何被优化的计算内核，都保留一份慢的、显然正确的参考实现，
用差分测试把两者钉住。参考实现允许慢一千倍。

**Why**：这个领域的错误是无声的。一个算错的数字仍然是个像模像样的经济体，
不崩溃、不触发断言、图还好看。而用户会拿输出去写论文。

上游有一处实例：`solution-5` 的表达式把 `b3·k·log(p3)` 写成了 `b3·k·log(p2)`，
源头是符号推导结果的人工转录，没有任何机制能拦住。见
[研究/上游代码问题.md](../研究/上游代码问题.md)。

**How to apply**：配套跑 `spec.md` 里那批不变量——物料平衡、预算恒等、非负性、
价格零次齐次。这些能陈述成一条律，正好是属性测试的靶心。

## 2026-09-05

### 发散检测的代价由 prefab 消除，不削弱 `iterate` 的检查语义

**决策**：`HahnelSlides2020` 把消费需求按商品类别拆成两块算，`plan_of` 直接递交私人品那块。
`iterate` 的检查面仍是计划实物层的四个数组，一个字不改。

**Why**：默认配置每轮都把状态翻成 `Plan` 供有限性检查，实测占单次运行的 31% 到 38%
（dep1ex01：带检测 1.32 秒，不带 1.00 秒）。代价不在检查，在 `plan_of` 对消费矩阵的花式索引——
整数索引数组必然复制，dep1ex 上一轮 24 MB。拆开算之后 `plan_of` 不再索引，
开销降到 8% 到 14%，剩下的是有限性扫描本身。

这块复制在不开检测的运行里也一样发生，所以修了是所有配置都省。
代价是拆成两块矩阵、两次 `bincount` 本身有开销：不带检测时新写法慢约 5%，
带检测时（默认）快约 13%。

**排除方案**：

- 保持现状 — 每个用这个 prefab 的人都付 31% 到 38%，而其中大部分是一次不必要的复制
- 给 `iterate` 加只查生产侧的轻量钩子 — 「计划实物层」从此有两个含义，学者自写的 `plan_of`
  也要知道这个区分。而「消费侧不会先发散」是从一个机制归纳出的经验命题，
  写进 `iterate` 等于让基础层替所有机制承诺它，违反理论无关这条硬约束，
  见 [不变量与指标.md](不变量与指标.md)

**How to apply**：`iterate` 的检查面是库对所有机制的承诺，不因为某个 prefab 嫌贵就削。
prefab 的表达方式贵，改 prefab。
