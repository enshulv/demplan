# 技术选型

## 2026-08-28

### Rust 写核心，Python 绑定作为第一用户接口

**决策**：核心计算用 Rust。通过 PyO3 与 maturin 提供 Python 绑定，文档以 Python API 为主，
Rust crate 作为同样受支持的下层。TS/wasm 负责可视化与人在环前端，不参与计算。

**Why**：三个理由。

第一，目标用户是经济学者与社会科学研究者，不是工程师。Concordia 与 AgentSociety 都用 Python，
因为研究者在那里。只提供 Rust 接口会让采用率接近零。

第二，Rust 适合核心：负载是 10⁴–10⁷ 实体上的定点迭代，需要跨平台可复现的确定性，
无 GC 停顿，单文件分发。

第三，Rust 编 wasm 后，同一个内核有三个出口——原生、Python、浏览器。
「民主」计划的落点最终是真实议会提交提案，那是 Web 应用，这个位置早晚要占。

**排除方案**：

- 纯 Rust，不提供 Python 接口 — 见 [被否决/技术选型.md](被否决/技术选型.md)
- 纯 Python — 见 [被否决/技术选型.md](被否决/技术选型.md)

**How to apply**：设计扩展点时，把 Python 可实现的接缝开在 `Procedure` 层。
`Procedure` 每轮调用一次（量级 10²），`Participant` 每轮调用一次每个主体（量级 10⁷）。
需要自定义 `Participant` 行为时走向量化回调：一次传整个人口的数组，不是每个主体调一次。

---

### 研究平台优先，学术输出放在外层包装

**决策**：一切设计服务于「跑实验、出图、写论文」。Rust 侧只产出长格式 Arrow/Parquet，
绘图与 LaTeX 表格导出在 Python 层。

**Why**：另一条路是「可部署系统优先」，那意味着一开始就要认真对待持久化、并发提交、
身份与授权，数据模型也会不同。两条路只能选一条，而本项目的目的是减少研究者的重复劳动。

期刊要的是可编辑的矢量 PDF，不是 PNG，所以绘图不能在 Rust 侧做死。

**How to apply**：仓库里放一个 `paper/` 目录，一条命令重现某篇已发表论文的全部图表。
这是最强的采用论证。

## 2026-09-05

### v1 的 Rust 表面刻意压小

**决策**：v1 的 Rust 只放四样：`Economy` 与 `Plan` 的列式存储与 schema 校验、
数据加载器、差额计算、Parquet 输出。柯布-道格拉斯闭式解、`iterate`、prefab、
参照解都在 Python（numpy 与 scipy）。

**Why**：协调方法是任意 Python，最重的计算在学者那一侧。
场景级并行因为 Python 回调只能走多进程，Rust 线程帮不上。
这个规模下 numpy 单轮 127 毫秒已经够用（2026-09-05 本机实测，dep1ex01，14 轮 1.77 秒）。

Rust 在 v1 兑现的是：加载速度（numpy 版解析 dep1ex 要 4.5 秒）、确定性归约、
Parquet 输出，以及为 v2 与 wasm 占位。

**How to apply**：任何「把 X 挪进 Rust」的提议，先量出 Python 版的瓶颈再谈。

---

### 仓库布局与 Python 侧数据类

**决策**：单仓 Cargo workspace，maturin 混合布局：

| 路径 | 内容 |
|---|---|
| `crates/cyberstride-core` | 数据模型与加载器，不依赖 Python |
| `crates/cyberstride-py` | PyO3 绑定，模块名 `cyberstride._core` |
| `python/cyberstride` | Python 包 |
| `tests/` | pytest 与 hypothesis |

Python 侧的 `Economy` 与 `Plan` 是不可变数据类，字段是 numpy 数组。
`_core` 返回数组时做一次拷贝，Python 侧持有。
错误呈现：Rust 返回 `Result`，绑定层转成 Python 异常，异常类型继承 `ValueError`。

开发循环用 `maturin develop`（调试构建），计时验收用 `--release`。
本机实测 release 构建 58 秒。

**Why**：丙档机械决策。一次拷贝在 50 MB 量级是毫秒级，不值得为零拷贝引入生命周期约束。
