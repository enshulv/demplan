# 数据模型

> 中文「协调方法」对应 `Procedure`，「演化规律」对应 `advance`。代码一律英文。

## 2026-08-30

### 商品用一张表加类别标记，不分表

**决策**：所有商品放同一张表，每条带一个类别标记。dep1ex 现有五类：
私人消费品、公共品、中间品、自然资源、劳动。自然资源与劳动也在这张表里，
它们同样有价格、同样参与调价。

**Why**：加新类别时只是多一个标记值，不改结构。本项目 v1 就要带排放扩展，
之后还要加货币存量，都会往这张表里加东西。

分成五张表在类型上更安全，但 `research/bench/repro.py:137` 那段
`np.where(cat == 0, ..., np.where(cat == 1, ...))` 说明实际计算里经常要统一处理，
分表会把这类操作变成五路分支。

**排除方案**：见 [被否决/数据模型.md](被否决/数据模型.md)

---

### `Plan` 分实物层与扩展层，扩展层留自由袋

**决策**：`Plan` 的核心是**实物配置**，理论无关，所有机制都有：

```
Plan（第 t 期）
├── 生产侧：每个生产单元 → 产出（按商品）、投入用量（按商品）
├── 消费侧：私人品「谁分到多少」、公共品「总共产多少、共享」
└── 禀赋使用：用掉多少自然资源、多少劳动
```

估值量是**扩展层**：库预定义常见的几种（指示性价格、劳动价值、影子价格），
同时留一个自由袋，学者可以放库没预见的估值方式。

**Why**：`Plan` 的字段集本身就是理论承诺——固定写成「数量加价格」等于宣称计划必然包含价格，
而劳动时间那一派的计划里没有价格。

分层的位置有一个独立验证：拿四条不变量核对，理论无关的两条（物料平衡、非负性）
只用实物层就能算，带理论的两条（预算恒等、价格零次齐次）才要扩展层。
**这不是巧合——实物配置是所有流派都承认的事实，价格才是分歧所在。**

因此「可计算才算、N/A 不是 0」那条规则在数据结构上自然成立：
劳动时间机制的 `Plan` 里根本没有价格那一格，价格类检查自动是 N/A。

留自由袋是因为封闭枚举会让学者为了加一种估值方式而等库发版，
撞上 [协调方法.md](协调方法.md) 那条「扩展机制是接口，不是库维护的清单」。

**How to apply**：投入用量必须存进 `Plan`，不能当派生量省掉。
Leontief 下它确实是派生的（产量乘固定系数），但技术一旦允许替代
（柯布-道格拉斯），**同样的产出可以有不同的投入组合，投入组合是机制选出来的决策**。
而 `Technology` 从第一天就是可扩展类型，要按可替代的情况设计。

### `Economy` 跨期可变

**决策**：`Economy` 是**某一期的状态**，不是一道不变的题目。多期时它被演化规律更新：

```
Economy₀ ──solve──> Plan₀ ──┐
                            ├──演化规律──> Economy₁ ──solve──> Plan₁ ──> ...
                            ┘
```

**Why**：让 `Economy` 恒定不变，等于把一条理论假设焊进数据模型——
**技术固定不变、投入比例固定不变**。一旦要研究技术进步、资源耗竭、人口变化，
这个假设就不成立，而长期可持续性正是民主计划经济争论的主战场之一。

理论预设写在数据模型里比写在检查里更隐蔽，因为没有任何一条检查会提示它的存在。

与 [分期与粒度.md](分期与粒度.md)「时间维度从一开始就进数据模型」不冲突，
但那条讲的是**一次性多期**（跨期优化，一次解出 T 期全部计划，`Economy` 不变），
本条讲的是**滚动多期**。两者都合法，`Economy` 同时容纳：
它既带 T 期的已知数据（未来禀赋、人口预测），又能被推进到下一期。
静态还是滚动由学者选，见 [演化规律.md](演化规律.md)。

**排除方案**：见 [被否决/数据模型.md](被否决/数据模型.md)

**How to apply**：v1 用 dep1ex，单期，跑起来用不到演化规律。
但接口现在就要按「`Economy` 是一期的状态」设计——
若写成不可变的题目，以后加演化规律要改所有协调方法的签名，那是重写。

### 变长投入用扁平数组加偏移量存储

**决策**：每个生产单元的投入品数不同（dep1ex 里从个位数到十几个不等）。
存成一根扁平数组加一张「每个单元从第几个开始」的偏移表，不用补齐成矩形。

**Why**：补齐成矩形（`research/bench/repro.py` 现在的做法）在投入品数分布不均时
大量内存是空的。扁平加偏移紧凑且连续，符合 [性能架构.md](性能架构.md)
「列式 f64 数组、全经济体常驻内存」。

这一条是内部实现，没有对外后果，不影响任何学者可见的行为。

## 2026-09-05

### 价格不进 `Economy`

**决策**：`Economy` 不含价格列。估值量只存在于两处：`Plan` 的扩展层，
以及协调方法自己的 `State`。热启动的起始价格由协调方法自己持有，作为它的参数或 `State`。

**Why**：`Economy` 是固定层，固定层理论无关。价格是估值量，
劳动时间直接计算那一派的 `Economy` 里没有价格这一列。
2026-08-30「商品用一张表加类别标记」里写「同样有价格、同样参与调价」，
那句描述的是 dep1ex 数据在 parecon 下的用法，不是 `Economy` 的字段。
把它留在 spec 里，阶段 0 就会把价格列写进固定层。

**部分收窄**：本条收窄 2026-08-30「商品用一张表加类别标记，不分表」中
「同样有价格、同样参与调价」这一句。一张表加类别标记这个结构本身不变。

**How to apply**：需要价格的检查（预算差额）从 `Plan.valuation` 取；
需要价格的协调方法自己初始化价格。

### `Economy` 分固定核心与命名扩展列，与 `Plan` 同构

**决策**：`Economy` 由三张列式表组成：商品、生产单元、消费单元。
每张表有一组固定列，加一个 `extra` 命名数组袋。

固定列只放各流派都承认存在的东西：标识符、分组、商品类别、禀赋、产出商品、
技术类型与技术参数（投入商品、投入系数、规模系数）。

行为参数——dep1ex 里生产单元的 `c`、`s`、`du`，消费单元的效用指数与消费额度——
进 `extra`，键名由库文档约定，由 prefab 解释。

**禀赋是商品表的一列**：本期不经生产就可用的数量。产出品为 0，
dep1ex 的自然资源与劳动各为 1000。

**Why**：生产函数的形状可以做成可扩展类型，但行为参数每一项都是某一派的主张
（努力负效用的形状、柯布-道格拉斯效用、外生消费额度）。
放进固定列违反理论无关；不放进 `Economy` 则 dep1ex 加载器无处安放它们，
演化规律也没法更新它们。命名扩展列与 `Plan` 扩展层的自由袋是同一个模式。

**排除方案**：

- 每类行为参数一张专门表 — 每复现一篇文献就要加一张表，撞上
  [协调方法.md](协调方法.md)「扩展机制是接口，不是库维护的清单」

**How to apply**：约定键名写进 `spec.md`。加载器写入 `extra` 的每个键都要在文档里
说明来源与含义。

### `Plan` 扩展层预定义 `income` 槽位

**决策**：`Plan.valuation` 的预定义键增加 `income`（按消费单元）。
预算差额在 `valuation` 同时含价格与 `income` 时可算；`income` 缺席时
回退到 `Economy` 消费单元 `extra` 的 `entitlement`；两者都没有则为 N/A。

**Why**：预算差额要每个参与者的收入。实物层没有它，原扩展层列的三种估值量也没有它。
不补这一格，预算差额对所有机制都是 N/A。

### 单产出单元；禀赋使用是派生量

**决策**：v1 每个生产单元恰好一种产出商品。禀赋使用不存进 `Plan`，
由投入用量按商品聚合得到。

**Why**：dep1ex 与投入产出表（对角 make 表）都是单产出。多产出以后通过加一根
`output` 扁平数组扩展，不改现有列的身份。禀赋使用是投入用量的确定性聚合，
存两份会漂。

**部分收窄**：本条把 `spec.md` 实物层的「禀赋使用」从存储项改为派生项。
2026-08-30「`Plan` 分实物层与扩展层」的其余内容不变。

### `Plan` 加 `extra` 袋；dep1ex 的技术是带 effort 因子的柯布-道格拉斯

**决策**：`Plan` 增加 `extra: Mapping[str, ndarray]`，与 `Economy` 三张表的 `extra` 同一模式：
命名数组，第一维等于 `n_units`、`n_consumers` 或 `n_commodities` 之一。
prefab `hahnel_2020_slides` 写两个约定键：`effort`（f64[n_units]）与 `consumer_demand`（f64[n_commodities]，
消费议会的申报量对每种商品需求的贡献）。第二个键原名 `public_demand`、只记公共品，2026-09-05 推广（见下）。

**Why**：红方总检察（2026-09-05）独立对上游 Clojure 核出 dep1ex 的生产函数是
`Q = a · e^c · Π x_j^{b_j}`，`e` 是每个单元每轮选出的 effort，`c`（`effort_c`）是它在生产函数里的指数，
不只是行为参数。上游八份闭式解都返回 effort，加载器此前丢弃它。
不记录 effort，`Plan` 就重建不出「产出与投入满足什么技术关系」这个指标——
dep1ex01 收敛计划上只有 34/30000 个单元满足声明的柯布-道格拉斯关系，中位偏离 8.6%。

公共品同理：`provision` 是供给，消费者对公共品的表述需求没有位置，物料平衡对公共品恒为 0。

两个量都是机制特有的实物量，不是估值量，放 `valuation` 不对；放固定列又把 dep1ex 的模型焊进实物层。
所以开一个与 `Economy.extra` 同形的袋。

**部分收窄**：本条收窄本文 2026-09-05「`Economy` 分固定核心与命名扩展列」里
对 `effort_c` 的描述（「行为参数」）。`effort_c` 同时是技术参数；`effort_s`、`effort_k` 仍是行为参数。
`technology_kind = 1` 对 dep1ex 的含义是「投入侧是柯布-道格拉斯」，完整生产函数还带 effort 因子，文档要说明。

**How to apply**：`tools.cobb_douglas` 给出的是不含 effort 的投入束，与 prefab 的投入组合不同，工具文档写明。

### dep1ex 加载器的 `n_goods` 只从投入编号推出，并检查分段编号不越界

**决策**：`n_goods` = 三段投入编号的最大值，不并入 `:product`。`:product` 与投入编号必须落在各自区段的
`[1, 区段大小]` 内，越界报 `LoadError`。

**Why**：`:product` 对 `:industry 0` 编的是私人品、对 `:industry 2` 编的是公共品，与中间品／自然资源／劳动不共享编号空间。
并入最大值会在私人品或公共品种类多于其他类时凭空造出带禀赋、无需求的商品，任何调价机制永不收敛。
dep1ex01 到 05 五类各 100 种，看不出来；红方手造档案（4 私人品、投入编号到 3）复现出 3 个幻影商品、250 轮不收敛。
越界编号则会静默改写商品类别。

这条是主 agent 施工单写错的规则（「全部 `:product` 与三段里出现的最大编号」），蓝方按字面实现并在报告里质疑过，
主 agent 没有处理。差分测试的 fixture 又照抄了实现的规则，所以没有任何执行者转红。

**How to apply**：差分测试的期望值必须来自独立的参考（`repro.py:223`），不能围着实现画。

### 效用指数列可以指向任何类别的商品，拆分判据是「是不是私人品」

**决策**：`utility_exponent_commodity` 的一列指向的商品，`commodity_kind` 可以是五类中的任何一类。
`hahnel_2020_slides` 把消费需求按「这一列的商品是不是私人品」分成两块：私人品那块就是
`Plan.consumption`，其余的（公共品，以及既非私人品也非公共品的商品）按各自的定价规则
算进商品需求。

**Why**：私人品那块要原样交给 `Plan.consumption`，必须独立成一个连续数组。其余的只在聚合里
用一次就扔，再往下拆买不到任何东西。

按「私人还是公共」二分会静默丢掉第三种列——那笔需求会改变价格路径与收敛轮数，
却不会有任何东西报错。

**排除方案**：

- 按「私人还是公共」二分 — 见上，第三种列被丢掉
- 拒收第三种列 — 它不是病态声明。算出来的需求与价格路径都对，只是没进计划记录。
  拒收等于替学者裁定「家庭不直接消费自然资源」这条经济学立场；而把自然资源重标成私人品，
  会连带让它的生产用量退出 `Plan.endowment_use` 的禀赋核算。库给数字，不给判词，
  见 [不变量与指标.md](不变量与指标.md)

**How to apply**：读 `commodity_kind` 的代码按五类写，不按「私人／公共」写。
第三种列的需求由 `consumer_demand` 记录，见下一条。

### `public_demand` 推广成 `consumer_demand`，覆盖三类列

**决策**：`Plan.extra` 的约定键 `public_demand` 改为 `consumer_demand`，`f64[n_commodities]`，
记消费议会的申报量对每种商品需求的贡献：私人品记各议会之和（等于 `total_consumption`），
公共品记全社会只算一次的共享量，其余商品记不除的合计，无人申报的商品为 0。
旧键等于 `np.where(public_commodity, consumer_demand, 0.0)`，可推导，因此不保留、不并存。

**覆盖**：2026-08-30 `Plan` 加 `extra` 袋那条里「写 `public_demand`」这个事实；
该条决策的其余部分仍然成立。

**Why**：效用指数指向既非私人品也非公共品的商品时，那笔需求会计入商品需求、参与失衡、
改变收敛轮数，然后在计划里查无此人——拿这份计划重算物料平衡，算出来的是另一个经济体。
这正是当初把 `public_demand` 放进 `extra` 要解决的毛病，只是当时只想到公共品。

推广而不是并列加键，是因为三类列记的是同一件事：这一轮进入物料平衡的消费侧需求。
分成两个键会让读者以为它们是两种量。

顺带修好 README 物料平衡例子的一处缺项：原来写
`total_input_use + total_consumption + public_demand`，有第三类列时缺项；
现在是 `total_input_use + consumer_demand` 两项。

**排除方案**：

- 新加一个键只记第三类列 — `extra` 那张表继续不对称，读者要自己拼三个键才拿得到消费侧需求
- 保留 `public_demand` 与新键并存 — 冗余，两份必然漂移

**How to apply**：`extra` 的键不由 `Plan.validate` 强制，这条不变。
推广一个已登记的约定键在没有外部用户时是零成本，有了就贵——发现约定键画错了范围要趁早改。

### `Plan.extra` 的两个约定键导出常量，`Economy.extra` 的不导出

**决策**：`Plan.extra` 的 `effort` 与 `consumer_demand` 各有一个导出常量
（`EFFORT`、`CONSUMER_DEMAND`），进 `__all__`。`Economy` 三张表的 `extra` 键
（`entitlement`、`utility_exponent`、`utility_exponent_commodity`、`effort_c/s/k`）
保持裸字符串。判准是：**读一份计划所必需的共同词汇才导出常量。**

**Why**：可比性靠原始输出，不靠读懂对方的代码（[协调方法.md](协调方法.md)）。
两个学者比较各自的运行，必须用同一个字符串指同一件事；一个把键拼成 `efort`，
两次运行事后就拼不到一起，而且当场没有任何报错。`Plan` 的文档已经写明，
没有这两个键就从计划重建不出生产函数与物料平衡——它们是读计划的必需品，不是某个机制的私事。

`Economy.extra` 的键不满足这条：它们是机制的输入参数，读计划的人不需要它们。

**排除方案**：

- 两个袋子都不导出 — `valuation` 已经导出四个常量，不一致；且拼错键没有任何东西会发现
- 两个袋子都导出 — 会让人以为库校验这些键，而 spec 明写「存在与否由加载器与 prefab 决定，
  库不要求」。`Economy.extra` 的键升格没有对应的读者
- 按「库层代码读不读」定 — 现在库层代码一个 `extra` 键都不读（差额工具箱还没写），
  按这条判准清单是空的，而问题今天就存在

**How to apply**：以后新增约定键时问一句——**不认识这个键的人还能不能读懂这份计划？**
不能，就导出常量。

### `unit_group` 是任意分组标签，库不校验取值范围

**决策**：`unit_group` 的取值定义为任意分组标签，不要求落在 `[0, n_groups)`，
`validate` 不查。spec 的字段表里写明。

**Why**：库里没有任何代码按 `unit_group` 聚合，定了范围也没有消费者，是一句空承诺。
而 `n_groups` 这个字段不存在，要么新增、要么用 `max + 1` 反推——后者让范围校验自动恒真。

更要紧的是 [研究/wiod-字段映射.md](../研究/wiod-字段映射.md) 已经查出 `unit_group` 只有一层，
「按行业分组」与「按经济体分组」表达不了两种。此时把它钉成稠密下标，
等于提前替阶段 3 做决定。

**排除方案**：要求落在 `[0, n_groups)` — 见上，既无消费者又与阶段 3 的候选方案冲突。

### `Plan` 的固定字段按字段可选，`consumption` 与 `provision` 先动

**决策**：`Plan` 的固定字段改为可缺席，粒度是**单个字段**而不是字段组。
本轮范围只含 `consumption`（连同 `consumption_commodity`）与 `provision`；
`output` 与 `input_use` 不动。配对关系单独立守卫：
`consumption` 与 `consumption_commodity` 必须同进同出，缺一个直接报错。

**缺席必须是学者声明出来的**，不是漏填。「计划里该有什么」属于学者构建计划的过程，
责任在他，缺席与声明不符直接报错。但**声明的负担要小**——不能为了这条让写一个机制变难。

**部分覆盖**：2026-08-30「`Plan` 分实物层与扩展层，扩展层留自由袋」里
「固定字段一律必填」这一点。分层与自由袋的划分本身不变。

**Why**：固定层里塞了带理论承诺的东西，而基础层不预设经济理论是硬约束
（[不变量与指标.md](不变量与指标.md)）。2026-09-05 的设计对抗审查逐条查出：

- `consumption` 是「私人品逐消费单元分配」，承诺了消费的排他性与「存在可识别的消费单元」。
  只做总量平衡的投入产出式机制没有这个量
- `provision` 是一种公共品一个标量，即萨缪尔森式纯公共品，全社会等量。
  区域性供给、分级供给表达不了
- `output` 与 `input_use` 接近中性，任何规划生产的机制都有，所以不在本轮范围

按字段而不按组，是因为字段粒度更灵活，而组的边界一旦划错要重划；
配对关系用一条显式守卫补上，比把它编进分组更直接。

**排除方案**：

- 按层（字段组）可选 — 组的边界要先定，而 `output`/`input_use` 这类中性字段也要被迫归组
- 不区分「声明缺席」与「漏填」 — 漏填变成静默，正是本库反复在防的那类失效
- 缺席时访问器返回零 — 库有一个量、按类别丢弃、另一边全额计入，两边不闭合。
  这正是 `endowment_use` 现有缺陷的形状

**How to apply**：访问器遇到它需要的字段缺席时，**报出明确说明缺了什么、该怎么补的异常**。
使用者是学者不是工程师，不该靠读栈追原因；泛用异常只做兜底。

### 申报量与配置量：一个字段加子类特化

**决策**：`consumption` 保持一个字段，含义取**最广义**——「消费侧的量」。
特化用子类表达，遵循里氏替换：

```
Plan                    最广义，不声明是哪一种
 ├─ StatedPlan(Plan)     consumption 是消费议会的申报量
 └─ AllocatedPlan(Plan)  consumption 是解出来的配置量
```

子类不收窄父类任何契约，只多一个声明；不带标识就是默认的最广义行为。
差异呈现按类型判：两侧同类才相减，异类拒绝并说明。

**Why**：这两种量今天已经在同一个字段里了，而且没有任何东西发现。2026-09-05 实测：
prefab 的 `consumption` 是 `_demand` 算出的申报矩阵，参照解的是 LP 解经 `allocate` 分下去的配置，
`validate` 两边都过。dep1ex01 收敛后每种私人品被多产 3.04% 到 3.35%——那份计划不是一个可行配置。

后果是可比性静默失效：学者算「未满足需求 = 申报 − 交付」，参照解那边结构性恒为 0，
prefab 那边是 3% 上下，而这个差别是两个字段含义不同造成的，不是经济学。

保留一个字段而不是拆成两个，是因为**目前没有机制同时产出两种量**——prefab 只有申报，
参照解只有配置。拆字段会造出一个今天没有用户的空槽。

「提案／申报」这个概念本来就被认定为数据模型不能丢的东西：
[分期与粒度.md](分期与粒度.md) 立「地面真相是生产单元集合不是矩阵」时的原话是
「矩阵里的一行没有『提案』这个概念，而议会是决策主体」。本条把它落到 `Plan` 上。

**排除方案**：

- 拆成两个字段 — 造一个没有用户的空槽，且 `consumption` 这个名字要废弃或重定义
- 语义放进一个字符串标记袋 — 序列化省事，但语义变成运行时数据，拼错要靠约定键兜
- 语义挂在层声明上 — 同一层里两个字段语义不同就表达不了

### 商品类别放开，但与「类别属性可声明」一起做

**决策**：`CommodityKind` 的白名单校验放开（`economy.py` 与 Rust 侧两处），
**但不单独放开**——同时把类别的属性从写死改为可声明：这个类别可不可消费、
算不算禀赋、进不进哪一层。

**Why**：单独放开买不到什么。查证如下：

- **排放不是被枚举挡住的，是被「一单元一产出」挡住的。** `output_commodity` 每个单元一个值，
  排放的自然建模是联产品。绕道都不干净：负投入系数在 Leontief 与柯布-道格拉斯工具里没有定义；
  给每个单元挂一个排放单元会让单元数翻倍并搞乱 `unit_group`
- **货币存量也不是。** CLAUDE.md 的已推迟清单写的是「加**字段**，不改行的身份」，
  而 spec 把它举成「加类别」的例子——两处本来就矛盾，见下条修正
- 真正买到的只有一件：学者用库不认识的标记做私有分类而不必 fork

而 `objectives.py` 的 `_require_consumable_support` 把未知类别一律拒收。
**开着的枚举加写死的属性 = 一个没有语义的标签**：学者能贴，贴了库的任何工具都不认。
所以放开必须和属性可声明配套。

**排除方案**：

- 只放开白名单 — 见上，半开
- 保持封闭并把 README 与 spec 的「可扩展」改成诚实说法 — 2026-09-05 一度采纳，
  后按「不受分期限制」重新评估后否决：诚实但把扩展这条路关死

**How to apply**：四处按类别分派的代码（`objectives.py` 的可消费判定与 `_split_equally`、
`plan.py` 的 `_ENDOWED_KINDS`、`reference.py` 的可消费掩码）都要改成读声明的属性，
不是读写死的元组。改不到的地方**报错，不许静默归零**——静默归零会给每个新类别配一个
「量影响结果却不进记录」的缺陷。

### 生产单元可以有多个产出（联产品）

**决策**：`Economy` 的单元表放开「一单元恰好一种产出」的限制，支持联产品。

**Why**：这是排放实验的钥匙，而排放在纲领里是明写的用例。钢与 CO₂ 由同一个单元同时产出，
这个结构现在表达不了，与商品类别开不开无关。固定资本与斯拉法式联合生产同样卡在这里。

**排除方案**：把排放建模成负的投入系数 — 库的两个技术工具对负系数没有定义；
给每个生产单元再挂一个排放单元 — 单元数翻倍，`unit_group` 的含义被搞乱。

**How to apply**：`output_commodity` 与相关的 `bincount` 聚合（`Plan.total_output`、
prefab 的 `_aggregate`、参照解的约束矩阵）都建立在一单元一产出上，逐处要重看。
这条比 `Plan` 分层动得更深，单独排一条交付线。

### 联产品的交付顺序从最后提前，与 `Plan` 分层同期评估

**决策**：联产品不再排在交付线的最后。它与 `Plan` 分层、类别属性放开一起进入同一轮排期评估，
具体先后按施工依赖定，不按「动得深就往后放」定。

**Why**：2026-09-05 调研三个同类实现时，`pablovegan/Economic-Planning` 带
`pollutants_constraint`，把生态上限当成常规约束跑在西班牙与瑞典的真实供给使用表上。
在此之前「排放被『一单元一产出』挡住」只有本项目自己的推理支撑；
现在有第二方的实现证据，而且 Szczepanczyk (2023) 列的七条未来方向里「环境影响」是其中一条。

原来的排期理由是「这条比 `Plan` 分层动得更深」。**改动深度是施工成本，不是优先级**。
按需要排而不按阶段表裁，见 [纲领定位.md](纲领定位.md) 2026-09-05。

**排除方案**：维持排在最后 — 排放是纲领里明写的用例，把明写的用例排在所有可选改进之后，
等于让交付顺序与纲领相反。

**How to apply**：这条只改**顺序**，不改
[上一条](#生产单元可以有多个产出联产品) 的决策内容与排除方案，两条并存。
排期评估时把「参照解的约束矩阵要重写」这一项算进成本，那是三处 `bincount` 聚合里最贵的一处。

### `Plan.valuation` 不校验 dtype 与长度，归到 `Plan` 分层那条线

**决策**：`Plan.valuation` 的数组既不校验 dtype 也不校验长度，这是一个已确认的缺陷。
**不在协调方法那一层补**，归进 `Plan` 分层可选化那条交付线一起做。

**Why**：2026-09-05 修 B2 时由蓝方的逃逸探针查出，三条症状同一个根因——

- 价格规则返回 `int64`，归档的 `indicative_price` 就是 `[893, 937, 704]`，
  而诚实值是 `[899.5, 943.8, 711.3]`
- 返回 `float32`，精度静默丢失
- 返回长一格的常数数组，15 个商品的经济体上归档 16 项，什么都不报

**这与 B2 是同一类缺陷**：归档的数字和实际用的数字不一致，而没有任何东西说出来。
区别在于 B2 的根在协调方法那一层，这条的根在 `Plan`。

补在 `PriceRule` 那一处只挡住一个调用方；`valuation` 是所有机制写估值量的公共出口，
任何一个机制返回错 dtype 都会静默归档，检查该在出口上。

**How to apply**：`Plan` 分层落地时一并做。检查两条——每个 `valuation` 数组是 `f64`，
长度等于 `n_commodities`。⚠ **拒收而不是转换**：静默把 `int64` 转成 `f64` 会把
「规则算错了类型」这个信号抹掉，等于用一个新的静默换掉旧的静默。

**一处连带的裁定**：`prefabs/hahnel_2020_slides._owned_copy` 是无条件的
`np.array(array, copy=True)`，没有 `isinstance` 守卫，因此规则返回 Python list 现在也能跑，
而此前会在下一轮索引时抛 `TypeError`。**保留这个写法**——它让「库拥有 `next_price`」
这条不变量无分支成立，而放宽的那一格正是上面这条检查将来要收回去的地方。

**相关**：[协调方法.md](协调方法.md) 2026-09-05「递给学者代码的数组是库自己拥有的拷贝」

### `Plan` 缺席用 `None` 声明，漏填仍由构造器报错

**决策**：把 2026-09-05「`Plan` 的固定字段按字段可选」那条落成可施工的规格。

**Why**：那条定了「按字段可选、缺席必须声明、声明的负担要小」三条原则，
但没定用什么表达缺席、访问器抛什么、设定文档从哪里读到声明。三处都是必须先定死的形状，
留着就等于让施工方自己选，而那正是 my-dev-flow 红线 8 要防的。

**`None` 就是缺席的声明。** 字段**不给默认值**，所以漏填仍然由 Python 的
「缺必需参数」直接报错，而显式写 `consumption=None` 是学者说出「我的机制没有这个量」。
声明的负担因此是一个词。

**排除方案**：另加一个 `absent=("consumption",)` 参数 — 同一件事要写两遍（字段给 `None`
再列一次名字），而两处不一致时还要再定一条规则。

**配对守卫**：`consumption` 与 `consumption_commodity` 必须同为 `None` 或同为数组，
只给一个直接报错。

**访问器抛专用异常** `PlanFieldAbsent`（继承 `SchemaError`）。讯息三段：
缺的是哪个字段、这个访问器为什么需要它、以及「若你的机制本来就没有这个量，
那么这个访问器对你不适用」。**不返回零**——库有一个量、按类别丢弃、另一边全额计入，
两边就不闭合。

**`Plan.absent_fields -> tuple[str, ...]`**，按字段声明顺序返回缺席字段名。
这是设定文档读「声明了哪几层」的唯一入口，签名钉死。

**`valuation` 校验**：每个数组必须是 `f64` 且长度等于 `n_commodities`，
**拒收，不转换**——静默把 `int64` 转成 `f64` 是拿新的静默换旧的静默。
这条兑现同日「`Plan.valuation` 不校验 dtype 与长度」那条的 How to apply。

**子类**：`StatedPlan` 与 `AllocatedPlan` 只多一个身份，不加字段、不收窄契约。
配套一个 `require_comparable(a, b)`：两侧同类或任一侧是基类 `Plan` 就放行，
一侧 `StatedPlan` 一侧 `AllocatedPlan` 则拒绝并说明差在哪。
**差异呈现组件本身不在本轮**——`决策/比较与呈现.md` 只定了原则没定清单，
现在做等于替那份清单预先选型。

**How to apply**：这些是可施工的形状，不是新的纲领。与上面几条冲突时以上面几条为准。

### `valuation` 按键校验长度：约定键按登记的行数，其余三选一

**决策**：推翻同日「`valuation` 的每个数组长度必须等于 `n_commodities`」那半条。新规则：

| 键 | 长度 |
|---|---|
| `indicative_price`、`labor_value`、`shadow_price` | `== n_commodities` |
| `income` | `== n_consumers` |
| 其他键 | 首维是 `n_units`、`n_consumers`、`n_commodities` 三者之一 |

`float64` 这条不变。报错讯息要能分开这两类：约定键说「这个键登记的是每 X 一个」，
非约定键说「首维必须是三者之一」。

**Why**：原来那半条是错的，施工时由蓝方顶回来。写它的时候只看到
`indicative_price` 与 `shadow_price` 两个约定键，两个都是每商品一个，
于是把「每商品一个」当成了 `valuation` 的通则。而 `income` 是**每消费单元一个**，
由 2026-08-30「`Plan` 扩展层预定义 `income` 槽位」立下，`README.md` 与 `spec.md` 都写着
`f64[n_consumers]`。一刀切会让那个槽位在 `n_consumers != n_commodities` 的任何经济体上失效。

新规则比一刀切**更严**：库认识自己约定的键，就按它知道的含义查精确长度；
不认识的键库不知道行数的含义，只能查三选一——与 `Plan.extra` 的
`_require_extra_rows` 同一模式，理由也同一条。

**部分覆盖**：本条推翻同日
[`Plan` 缺席用 `None` 声明](#plan-缺席用-none-声明漏填仍由构造器报错)
里关于 `valuation` **长度**的那一句。「拒收不转换」与 `float64` 两条不变。

**How to apply**：往 `valuation` 加新的约定键时，**同时登记它是每什么一个**，
否则它会掉进宽松的三选一那一档。

⚠ 写这条时清单漏了 `labor_value`，施工方按通则把它登记成 `n_commodities` 并顶回来——
依据是 `README.md` 与常量自己的文档（每种商品的体现劳动时间）。
**登记表就是那张清单**，不要把它散落在几处文字里；本条的表已经补全。

### `Plan` 分层的四处施工细节定案

**决策**：施工中问出来的四处，逐条定案。

1. **`absent_fields` 是属性**，不是方法。设定文档那边按属性消费，两侧已对齐。
2. **`absent_fields` 列出 `consumption_commodity`**，取字面义——返回所有为 `None` 的可选字段。
   它是**字段**的清单，不是「层」的清单。
3. **`require_comparable` 抛 `ValueError`**，不抛 `SchemaError`。
   `SchemaError` 的文档写的是「结构违规」，而可比性不是结构问题；
   `SchemaError` 继承 `ValueError`，所以 `except ValueError` 两者都接得住。
4. **`valuation` 的 dtype 查在 `__post_init__`，长度查在 `validate`。**
   `run()` 不调 `validate`，全放 `validate` 的话，「价格规则返回 `int64`、
   归档的是截断值」这个立这条决策的症状在 prefab 的默认路径上照样不会红。
   dtype 不需要经济体，长度需要 `n_commodities`——只有长度那一半必须留在 `validate`。

**Why**：四处规格都没写，而每一处都有不止一种做法。写下来是为了下次不用再问一遍。

**连带**：`iterate.py` 的 `_physical_arrays` 与 `checks.py` 的 `_differing_fields`
原本无条件读五个物理字段，缺席时崩在 `None` 上，**「字段可缺席」因此端到端不可用**。
两处一并修：发散判据只看实际存在的物理量（`iterate` 的文档要写明这条覆盖面的收窄）；
确定性比对里两侧同为缺席算相同，一侧缺席一侧有值算不同且要报成「一侧缺席」而不是数值差。

**How to apply**：往 `Plan` 加任何「读遍所有物理字段」的代码之前，先问它遇到 `None` 会怎样。
