# 数据模型

> 中文「协调方法」对应 `Procedure`，「演化规律」对应 `advance`。代码一律英文。

## 2026-08-30

### 商品用一张表加类别标记，不分表

**决策**：所有商品放同一张表，每条带一个类别标记。dep1ex 现有五类：
私人消费品、公共品、中间品、自然资源、劳动。自然资源与劳动也在这张表里，
它们同样有价格、同样参与调价。

**Why**：加新类别时只是多一个标记值，不改结构。本项目 v1 就要带排放扩展，
之后还要加货币存量，都会往这张表里加东西。

分成五张表在类型上更安全，但 `research/bench/repro.py:137` 那段
`np.where(cat == 0, ..., np.where(cat == 1, ...))` 说明实际计算里经常要统一处理，
分表会把这类操作变成五路分支。

**排除方案**：见 [被否决/数据模型.md](被否决/数据模型.md)

---

### `Plan` 分实物层与扩展层，扩展层留自由袋

**决策**：`Plan` 的核心是**实物配置**，理论无关，所有机制都有：

```
Plan（第 t 期）
├── 生产侧：每个生产单元 → 产出（按商品）、投入用量（按商品）
├── 消费侧：私人品「谁分到多少」、公共品「总共产多少、共享」
└── 禀赋使用：用掉多少自然资源、多少劳动
```

估值量是**扩展层**：库预定义常见的几种（指示性价格、劳动价值、影子价格），
同时留一个自由袋，学者可以放库没预见的估值方式。

**Why**：`Plan` 的字段集本身就是理论承诺——固定写成「数量加价格」等于宣称计划必然包含价格，
而劳动时间那一派的计划里没有价格。

分层的位置有一个独立验证：拿四条不变量核对，理论无关的两条（物料平衡、非负性）
只用实物层就能算，带理论的两条（预算恒等、价格零次齐次）才要扩展层。
**这不是巧合——实物配置是所有流派都承认的事实，价格才是分歧所在。**

因此「可计算才算、N/A 不是 0」那条规则在数据结构上自然成立：
劳动时间机制的 `Plan` 里根本没有价格那一格，价格类检查自动是 N/A。

留自由袋是因为封闭枚举会让学者为了加一种估值方式而等库发版，
撞上 [协调方法.md](协调方法.md) 那条「扩展机制是接口，不是库维护的清单」。

**How to apply**：投入用量必须存进 `Plan`，不能当派生量省掉。
Leontief 下它确实是派生的（产量乘固定系数），但技术一旦允许替代
（柯布-道格拉斯），**同样的产出可以有不同的投入组合，投入组合是机制选出来的决策**。
而 `Technology` 从第一天就是可扩展类型，要按可替代的情况设计。

### `Economy` 跨期可变

**决策**：`Economy` 是**某一期的状态**，不是一道不变的题目。多期时它被演化规律更新：

```
Economy₀ ──solve──> Plan₀ ──┐
                            ├──演化规律──> Economy₁ ──solve──> Plan₁ ──> ...
                            ┘
```

**Why**：让 `Economy` 恒定不变，等于把一条理论假设焊进数据模型——
**技术固定不变、投入比例固定不变**。一旦要研究技术进步、资源耗竭、人口变化，
这个假设就不成立，而长期可持续性正是民主计划经济争论的主战场之一。

理论预设写在数据模型里比写在检查里更隐蔽，因为没有任何一条检查会提示它的存在。

与 [分期与粒度.md](分期与粒度.md)「时间维度从一开始就进数据模型」不冲突，
但那条讲的是**一次性多期**（跨期优化，一次解出 T 期全部计划，`Economy` 不变），
本条讲的是**滚动多期**。两者都合法，`Economy` 同时容纳：
它既带 T 期的已知数据（未来禀赋、人口预测），又能被推进到下一期。
静态还是滚动由学者选，见 [演化规律.md](演化规律.md)。

**排除方案**：见 [被否决/数据模型.md](被否决/数据模型.md)

**How to apply**：v1 用 dep1ex，单期，跑起来用不到演化规律。
但接口现在就要按「`Economy` 是一期的状态」设计——
若写成不可变的题目，以后加演化规律要改所有协调方法的签名，那是重写。

### 变长投入用扁平数组加偏移量存储

**决策**：每个生产单元的投入品数不同（dep1ex 里从个位数到十几个不等）。
存成一根扁平数组加一张「每个单元从第几个开始」的偏移表，不用补齐成矩形。

**Why**：补齐成矩形（`research/bench/repro.py` 现在的做法）在投入品数分布不均时
大量内存是空的。扁平加偏移紧凑且连续，符合 [性能架构.md](性能架构.md)
「列式 f64 数组、全经济体常驻内存」。

这一条是内部实现，没有对外后果，不影响任何学者可见的行为。

## 2026-09-05

### 价格不进 `Economy`

**决策**：`Economy` 不含价格列。估值量只存在于两处：`Plan` 的扩展层，
以及协调方法自己的 `State`。热启动的起始价格由协调方法自己持有，作为它的参数或 `State`。

**Why**：`Economy` 是固定层，固定层理论无关。价格是估值量，
劳动时间直接计算那一派的 `Economy` 里没有价格这一列。
2026-08-30「商品用一张表加类别标记」里写「同样有价格、同样参与调价」，
那句描述的是 dep1ex 数据在 parecon 下的用法，不是 `Economy` 的字段。
把它留在 spec 里，阶段 0 就会把价格列写进固定层。

**部分收窄**：本条收窄 2026-08-30「商品用一张表加类别标记，不分表」中
「同样有价格、同样参与调价」这一句。一张表加类别标记这个结构本身不变。

**How to apply**：需要价格的检查（预算差额）从 `Plan.valuation` 取；
需要价格的协调方法自己初始化价格。

### `Economy` 分固定核心与命名扩展列，与 `Plan` 同构

**决策**：`Economy` 由三张列式表组成：商品、生产单元、消费单元。
每张表有一组固定列，加一个 `extra` 命名数组袋。

固定列只放各流派都承认存在的东西：标识符、分组、商品类别、禀赋、产出商品、
技术类型与技术参数（投入商品、投入系数、规模系数）。

行为参数——dep1ex 里生产单元的 `c`、`s`、`du`，消费单元的效用指数与消费额度——
进 `extra`，键名由库文档约定，由 prefab 解释。

**禀赋是商品表的一列**：本期不经生产就可用的数量。产出品为 0，
dep1ex 的自然资源与劳动各为 1000。

**Why**：生产函数的形状可以做成可扩展类型，但行为参数每一项都是某一派的主张
（努力负效用的形状、柯布-道格拉斯效用、外生消费额度）。
放进固定列违反理论无关；不放进 `Economy` 则 dep1ex 加载器无处安放它们，
演化规律也没法更新它们。命名扩展列与 `Plan` 扩展层的自由袋是同一个模式。

**排除方案**：

- 每类行为参数一张专门表 — 每复现一篇文献就要加一张表，撞上
  [协调方法.md](协调方法.md)「扩展机制是接口，不是库维护的清单」

**How to apply**：约定键名写进 `spec.md`。加载器写入 `extra` 的每个键都要在文档里
说明来源与含义。

### `Plan` 扩展层预定义 `income` 槽位

**决策**：`Plan.valuation` 的预定义键增加 `income`（按消费单元）。
预算差额在 `valuation` 同时含价格与 `income` 时可算；`income` 缺席时
回退到 `Economy` 消费单元 `extra` 的 `entitlement`；两者都没有则为 N/A。

**Why**：预算差额要每个参与者的收入。实物层没有它，原扩展层列的三种估值量也没有它。
不补这一格，预算差额对所有机制都是 N/A。

### 单产出单元；禀赋使用是派生量

**决策**：v1 每个生产单元恰好一种产出商品。禀赋使用不存进 `Plan`，
由投入用量按商品聚合得到。

**Why**：dep1ex 与投入产出表（对角 make 表）都是单产出。多产出以后通过加一根
`output` 扁平数组扩展，不改现有列的身份。禀赋使用是投入用量的确定性聚合，
存两份会漂。

**部分收窄**：本条把 `spec.md` 实物层的「禀赋使用」从存储项改为派生项。
2026-08-30「`Plan` 分实物层与扩展层」的其余内容不变。

### `Plan` 加 `extra` 袋；dep1ex 的技术是带 effort 因子的柯布-道格拉斯

**决策**：`Plan` 增加 `extra: Mapping[str, ndarray]`，与 `Economy` 三张表的 `extra` 同一模式：
命名数组，第一维等于 `n_units`、`n_consumers` 或 `n_commodities` 之一。
prefab `hahnel_2020_slides` 写两个约定键：`effort`（f64[n_units]）与 `consumer_demand`（f64[n_commodities]，
消费议会的申报量对每种商品需求的贡献）。第二个键原名 `public_demand`、只记公共品，2026-09-05 推广（见下）。

**Why**：红方总检察（2026-09-05）独立对上游 Clojure 核出 dep1ex 的生产函数是
`Q = a · e^c · Π x_j^{b_j}`，`e` 是每个单元每轮选出的 effort，`c`（`effort_c`）是它在生产函数里的指数，
不只是行为参数。上游八份闭式解都返回 effort，加载器此前丢弃它。
不记录 effort，`Plan` 就重建不出「产出与投入满足什么技术关系」这个指标——
dep1ex01 收敛计划上只有 34/30000 个单元满足声明的柯布-道格拉斯关系，中位偏离 8.6%。

公共品同理：`provision` 是供给，消费者对公共品的表述需求没有位置，物料平衡对公共品恒为 0。

两个量都是机制特有的实物量，不是估值量，放 `valuation` 不对；放固定列又把 dep1ex 的模型焊进实物层。
所以开一个与 `Economy.extra` 同形的袋。

**部分收窄**：本条收窄本文 2026-09-05「`Economy` 分固定核心与命名扩展列」里
对 `effort_c` 的描述（「行为参数」）。`effort_c` 同时是技术参数；`effort_s`、`effort_k` 仍是行为参数。
`technology_kind = 1` 对 dep1ex 的含义是「投入侧是柯布-道格拉斯」，完整生产函数还带 effort 因子，文档要说明。

**How to apply**：`tools.cobb_douglas` 给出的是不含 effort 的投入束，与 prefab 的投入组合不同，工具文档写明。

### dep1ex 加载器的 `n_goods` 只从投入编号推出，并检查分段编号不越界

**决策**：`n_goods` = 三段投入编号的最大值，不并入 `:product`。`:product` 与投入编号必须落在各自区段的
`[1, 区段大小]` 内，越界报 `LoadError`。

**Why**：`:product` 对 `:industry 0` 编的是私人品、对 `:industry 2` 编的是公共品，与中间品／自然资源／劳动不共享编号空间。
并入最大值会在私人品或公共品种类多于其他类时凭空造出带禀赋、无需求的商品，任何调价机制永不收敛。
dep1ex01 到 05 五类各 100 种，看不出来；红方手造档案（4 私人品、投入编号到 3）复现出 3 个幻影商品、250 轮不收敛。
越界编号则会静默改写商品类别。

这条是主 agent 施工单写错的规则（「全部 `:product` 与三段里出现的最大编号」），蓝方按字面实现并在报告里质疑过，
主 agent 没有处理。差分测试的 fixture 又照抄了实现的规则，所以没有任何执行者转红。

**How to apply**：差分测试的期望值必须来自独立的参考（`repro.py:223`），不能围着实现画。

### 效用指数列可以指向任何类别的商品，拆分判据是「是不是私人品」

**决策**：`utility_exponent_commodity` 的一列指向的商品，`commodity_kind` 可以是五类中的任何一类。
`hahnel_2020_slides` 把消费需求按「这一列的商品是不是私人品」分成两块：私人品那块就是
`Plan.consumption`，其余的（公共品，以及既非私人品也非公共品的商品）按各自的定价规则
算进商品需求。

**Why**：私人品那块要原样交给 `Plan.consumption`，必须独立成一个连续数组。其余的只在聚合里
用一次就扔，再往下拆买不到任何东西。

按「私人还是公共」二分会静默丢掉第三种列——那笔需求会改变价格路径与收敛轮数，
却不会有任何东西报错。

**排除方案**：

- 按「私人还是公共」二分 — 见上，第三种列被丢掉
- 拒收第三种列 — 它不是病态声明。算出来的需求与价格路径都对，只是没进计划记录。
  拒收等于替学者裁定「家庭不直接消费自然资源」这条经济学立场；而把自然资源重标成私人品，
  会连带让它的生产用量退出 `Plan.endowment_use` 的禀赋核算。库给数字，不给判词，
  见 [不变量与指标.md](不变量与指标.md)

**How to apply**：读 `commodity_kind` 的代码按五类写，不按「私人／公共」写。
第三种列的需求由 `consumer_demand` 记录，见下一条。

### `public_demand` 推广成 `consumer_demand`，覆盖三类列

**决策**：`Plan.extra` 的约定键 `public_demand` 改为 `consumer_demand`，`f64[n_commodities]`，
记消费议会的申报量对每种商品需求的贡献：私人品记各议会之和（等于 `total_consumption`），
公共品记全社会只算一次的共享量，其余商品记不除的合计，无人申报的商品为 0。
旧键等于 `np.where(public_commodity, consumer_demand, 0.0)`，可推导，因此不保留、不并存。

**覆盖**：2026-08-30 `Plan` 加 `extra` 袋那条里「写 `public_demand`」这个事实；
该条决策的其余部分仍然成立。

**Why**：效用指数指向既非私人品也非公共品的商品时，那笔需求会计入商品需求、参与失衡、
改变收敛轮数，然后在计划里查无此人——拿这份计划重算物料平衡，算出来的是另一个经济体。
这正是当初把 `public_demand` 放进 `extra` 要解决的毛病，只是当时只想到公共品。

推广而不是并列加键，是因为三类列记的是同一件事：这一轮进入物料平衡的消费侧需求。
分成两个键会让读者以为它们是两种量。

顺带修好 README 物料平衡例子的一处缺项：原来写
`total_input_use + total_consumption + public_demand`，有第三类列时缺项；
现在是 `total_input_use + consumer_demand` 两项。

**排除方案**：

- 新加一个键只记第三类列 — `extra` 那张表继续不对称，读者要自己拼三个键才拿得到消费侧需求
- 保留 `public_demand` 与新键并存 — 冗余，两份必然漂移

**How to apply**：`extra` 的键不由 `Plan.validate` 强制，这条不变。
推广一个已登记的约定键在没有外部用户时是零成本，有了就贵——发现约定键画错了范围要趁早改。

### `Plan.extra` 的两个约定键导出常量，`Economy.extra` 的不导出

**决策**：`Plan.extra` 的 `effort` 与 `consumer_demand` 各有一个导出常量
（`EFFORT`、`CONSUMER_DEMAND`），进 `__all__`。`Economy` 三张表的 `extra` 键
（`entitlement`、`utility_exponent`、`utility_exponent_commodity`、`effort_c/s/k`）
保持裸字符串。判准是：**读一份计划所必需的共同词汇才导出常量。**

**Why**：可比性靠原始输出，不靠读懂对方的代码（[协调方法.md](协调方法.md)）。
两个学者比较各自的运行，必须用同一个字符串指同一件事；一个把键拼成 `efort`，
两次运行事后就拼不到一起，而且当场没有任何报错。`Plan` 的文档已经写明，
没有这两个键就从计划重建不出生产函数与物料平衡——它们是读计划的必需品，不是某个机制的私事。

`Economy.extra` 的键不满足这条：它们是机制的输入参数，读计划的人不需要它们。

**排除方案**：

- 两个袋子都不导出 — `valuation` 已经导出四个常量，不一致；且拼错键没有任何东西会发现
- 两个袋子都导出 — 会让人以为库校验这些键，而 spec 明写「存在与否由加载器与 prefab 决定，
  库不要求」。`Economy.extra` 的键升格没有对应的读者
- 按「库层代码读不读」定 — 现在库层代码一个 `extra` 键都不读（差额工具箱还没写），
  按这条判准清单是空的，而问题今天就存在

**How to apply**：以后新增约定键时问一句——**不认识这个键的人还能不能读懂这份计划？**
不能，就导出常量。

### `unit_group` 是任意分组标签，库不校验取值范围

**决策**：`unit_group` 的取值定义为任意分组标签，不要求落在 `[0, n_groups)`，
`validate` 不查。spec 的字段表里写明。

**Why**：库里没有任何代码按 `unit_group` 聚合，定了范围也没有消费者，是一句空承诺。
而 `n_groups` 这个字段不存在，要么新增、要么用 `max + 1` 反推——后者让范围校验自动恒真。

更要紧的是 [研究/wiod-字段映射.md](../研究/wiod-字段映射.md) 已经查出 `unit_group` 只有一层，
「按行业分组」与「按经济体分组」表达不了两种。此时把它钉成稠密下标，
等于提前替阶段 3 做决定。

**排除方案**：要求落在 `[0, n_groups)` — 见上，既无消费者又与阶段 3 的候选方案冲突。
