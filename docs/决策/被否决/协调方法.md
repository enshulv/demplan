# 被否决：协调方法

## 2026-08-28

### v1 用预设算子拼装协调方法

**否决**（推迟，非永久排除。复活条件见末尾）。

**提案**：库提供一组算子（`excess_ratio`、`clamp`、`power_adjust`、`scale_prices` 等），
学者在 Python 里把它们串成一棵树。调用算子不执行计算，只描述计算；
整棵树在开跑时一次交给 Rust 解释执行。这是 polars 惰性表达式与 Keras 层堆叠的模式，
也是本项目最初设想的「polars 模式」。

**当初为什么想做**：三条收益。一是没有每轮跨语言；二是组装物是数据，内容哈希天然可靠；
三是方法可检视——一棵树能打印、能 diff、能归一化，一段任意 Python 不能。
第三条直接服务于「学者之间共享一套语言、互相检视」这个愿景。

**排除理由**：三条收益里只有第三条立得住，而第三条不在 v1 的目标里。

第一条不成立。协调方法一轮调一次、一次运行 10² 次，每轮碰的是五组长度 10² 到 10³
的价格向量（`research/bench/repro.py:118`），几十 KB。跨语言开销占比 0.1% 量级。
54.8 MB 那个数字是整个经济体，协调方法用不上它。

第二条只是更干净，任意 Python 也能哈希源码。

第三条真实，但 v1 的目标是「同一批数字，快得多、好用得多」，
复现的判据是同一份输入跑出同一批数字，用数值差分就能验，不需要读懂方法。
可检视性服务的是后续愿景，不是 v1。

工量上，算子方案要在 v1 之前花掉四件事：设计算子集、写解释执行器、
定序列化格式、定规范形式。而算子集一旦是扩展机制，**缺算子的学者就被堵在维护者身上**，
他的实际选择通常不是等发版，是绕过库自己写脚本，那条需求信号也就收不到了。

**复活条件**：接口层跑通、有真实用户之后。届时算子集作为**建在接口之上的便利层**加入，
不作为扩展机制——用算子拼的额外获得可检视性与结构化哈希，
写任意 Python 的仍然拿到其余全部能力。两条路是上下层，不冲突。

推迟的代价可控：先有接口、后加算子层时，已有的协调方法照跑不误，
因为它们本来就是通过接口接进来的，而算子组装最终也产出一个满足同一接口的东西。
按 [分期与粒度.md](../分期与粒度.md) 立的判准（现在不做、以后补的代价是不是重写），
这一条不构成重写。
