# 被否决：性能架构

## 2026-08-28

### 用数据库当计算基质

**否决**。

**提案**：把经济体存进 SQLite 或类似数据库，用 SQL 做需求计算与供需聚合，
迭代状态在数据库里原地更新。

**当初为什么想做**：这是上游实现在 2023 年的 `pe_ifb_compute` 与 2026 年的 `pequod-plus`
两次独立走上的路，所以它有真实的吸引力：数据装不进内存时，数据库是现成的答案。
聚合查询用 SQL 写也确实简洁。

**排除理由**：实测代价约 1450 倍——同规模一次实验 4 小时对不到 10 秒。
瓶颈是每轮 600 万行的磁盘往返与序列化，不是浮点运算。

而促使上游做这个选择的前提本身是假的：那个数据集实测常驻内存只有 54.8 MB。
撑爆 4 GB 堆的是装箱 map 的表示开销，不是数据量。**遇到内存墙时，
先量数据的真实大小，再决定是不是要下磁盘。**

**复活条件**：单次 run 的经济体确实放不进内存（v2 的 10⁷ 议会稠密布局约 30 到 40 GB，
接近这条线）。届时的正确解法是稀疏表示或分块流式，仍然不是把迭代状态放进数据库。
