# 被否决：数据模型

## 2026-08-30

### 商品按类别分成多张表

**否决**。

**提案**：私人消费品、公共品、中间品、自然资源、劳动各一张表。

**当初为什么想做**：类型上更安全，不会把劳动误当中间品用。

**排除理由**：加第六类要改结构，而本项目 v1 就要带排放扩展、之后还要加货币存量。
且 `research/bench/repro.py:137` 那段按类别取价格的三路 `np.where` 说明
实际计算里经常要统一处理，分表会把这类操作变成五路分支。

**复活条件**：类别数长期稳定、且误用类别成为实际 bug 来源时。

---

### `Plan` 的估值层用封闭枚举

**否决**。

**提案**：`Plan` 的估值部分定义成封闭枚举——指示性价格、劳动价值、影子价格、无。
类型安全，与 `Technology` 同构。

**当初为什么想做**：自由的键值袋没有类型保护，键名拼错会静默返回空。

**排除理由**：封闭枚举意味着学者要加一种库没预见的估值方式，就得改库的代码、等发版。
这与 [协调方法.md](../协调方法.md)「扩展机制是接口，不是库维护的清单」直接冲突，
也重演了算子方案里那个「缺一个就被堵在维护者身上」的问题。

最终取折中：库预定义常见的几种（有类型保护），同时留自由袋（罕见的走这里）。

**复活条件**：无。折中方案已覆盖两边的收益。

---

### `Economy` 全程不可变

**否决**。

**提案**：`Economy` 是一道不变的题目，协调方法只读它。多期就是把同一道题算 T 遍。

**当初为什么想做**：概念干净——题目与答案分离，`Economy` 是输入、`Plan` 是输出，
一次 run 的边界清楚，确定性也好保证。

**排除理由**：**它把一条理论假设焊进了数据模型——技术固定不变、投入比例固定不变。**
一旦要研究技术进步、资源耗竭、人口变化，这个假设就不成立，
而长期可持续性是民主计划经济争论的主战场之一。

理论预设写在数据模型里比写在检查里更隐蔽：没有任何一条检查会提示它的存在，
读者只会以为「这个库就是这么设计的」。

**复活条件**：无。与理论无关这条硬约束直接冲突。
