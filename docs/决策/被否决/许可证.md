# 被否决：许可证

## 2026-09-05

### 改用 GPL 并明确引用三个同类实现的贡献

**否决**。

**提案**：把本库从 MIT 改成 GPL，理由是新调研的三个经济计划实现
（`socialist_planning`、`EPOS`、`Economic-Planning`）都用 GPL，
换过去可以与它们对齐，并明确引用它们的贡献。

**当初为什么想做**：与领域内同行的许可证选择一致；直觉上换过去才好引用与复用它们的成果。
时间窗口也支持——本仓代码目前全部是单一作者的，改许可证零成本，
第一个外部贡献者进来之后就要挨个拿同意。

**排除理由**：

- **与第 5 条正面冲突。** GPL 的传染边界在衍生作品上。学者 `import cyberstride`
  写自己的 `Procedure`，一旦分发就得连带 GPL，而 spec 明写扩展实现「不需要并入本库代码」。
  受影响最重的正是本库的目标用户
- **「各家都用 GPL」是抽样偏差。** 三个样本同属一个政治光谱，GPL 在那里是立场声明。
  本库对标的是基础设施那一类，那一类几乎不用 GPL
- **换不到提案想要的东西。** 引用出处是学术规范不是许可证机制；
  照论文重实现在 MIT 下本来就合法，因为算法思想不受著作权保护
- **Rust 侧代价额外重**：crates.io 惯例是 MIT/Apache-2.0 双授权，GPL crate 无人敢依赖

**同时评估过的中间档**：MPL-2.0 是唯一能同时满足「有 copyleft」与「不撞第 5 条」的选项
（文件级 copyleft，学者自己的 `Procedure` 文件不受影响）。LGPL 在 Rust 与 Python 扩展模块上
的链接边界模糊，对学术库是负资产。Apache-2.0 比 MIT 多一条专利授权。
三者都没有采用，因为提案要解决的问题（引用、复用）根本不由许可证解决。

**复活条件**：与 [2026-08-28 那条](#2026-08-28) 相同——出现需要防止的具体商业挪用，
且届时已有足够用户基础承受采用率损失。当前用户数为零，两条都不满足。

## 2026-08-28

### 用 Coopyleft（CoopCycle 许可证）

**否决**。

**提案**：采用法国送餐骑手合作社联盟 CoopCycle 自订的 Coopyleft 许可证，
只允许合作社与欧盟定义下的社会团结经济主体使用本库。

**当初为什么想做**：与本项目的领域立场一致。做民主计划经济的基础设施，
用一个把使用权交给合作社的许可证，姿态是自洽的。

**排除理由**：它按使用者的法律形态设限，因此不符合 OSI 的开源定义，
后果对学术库是具体的——conda-forge 与 Debian 收不了非 OSI 许可证；
不少大学的法务与 IT 只批 OSI 清单内的许可证；越来越多期刊的可复现性要求指定开放许可证；
别的库不能依赖它。

还有一条内部张力：本项目的定位是「共用学术基础设施」，
而按机构形态限制谁能用，与「共用」是相反方向。

**复活条件**：本库出现需要防止的具体商业挪用，且届时已有足够用户基础承受采用率损失时。
