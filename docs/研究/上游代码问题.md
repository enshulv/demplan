# 上游代码问题

审查 `msszczep/pequod-plus`（branch `db`，HEAD `44a6d08`）与 `msszczep/pe_ifb_compute`
的结果。clone 在 `upstream/pequod-plus/`。

引用以函数名为主，行号仅作定位提示——上游仍在演进，行号会过期。

## 正确性

### 已发表的伪代码重现不了已发表的结果

**这是本次审查中影响最大的一条。**

2020 年会议报告用的调价规则是 `w = v(1.05 − 0.5ᵛ)`，`v > 0.25` 时取 `v = 0.25`，无递推。
2023 年论文的伪代码把开头那个 `v ×` 因子换成了「乘上一轮的增量，取小、取绝对值、
下限 0.001」。现行代码 `util.cljc` 的 `compute-surpluses-prices` 实现的是 2023 版。

在作者公开的 dep1ex01 数据、论文明写的禀赋 1000 下实测：

| 规则 | 冷启动 5% |
|---|---|
| 2023 论文伪代码（现行代码） | 不收敛，250 轮后最差失衡 30.2% |
| 2020 幻灯片公式 | 14 轮，与报告的 11.85 同量级 |

也就是说，**2023 年那篇专门为了让他人重实现而发表伪代码的论文，
其伪代码收敛不到已发表的结果。**

这解释了两件此前无法解释的事：

1. 上游自己的记录（`docs/notes.txt`）中冷启动是 41 到 96 轮，
   与 2020 年报告的 11.85 差一个数量级
2. 2026 年 8 月连续两次提交叫 "Fix oscillating behavior" 与
   "Fix extremely slow convergence"——作者在手工调这条递推，
   而问题出在递推本身，不在它的参数

详见 [复现记录.md](复现记录.md)。

### `solution-5` 的表达式转录错误

`src/clj/pequod_plus/csvgen.clj` 的 `solution-5`，`x1` 项里写的是 `(* b3 k log-p2)`，
按 `solution-4` 与 `solution-6` 的模式以及解析解，该处应为 `b3·k·log(p3)`，
而 `b3-k-log-p3` 整项缺失。

影响：恰好有五个投入品的工人议会，其第一种中间投入的需求量算错。

成因不是手滑，是方法论的系统性风险。论文说明这些表达式由 Wolfram Mathematica 的 `Solve`
生成后转写成 Clojure，`solution-3` 到 `solution-10` 共八份，无交叉校验。

### 公共品需求在两条路径上差 N 倍

`src/cljc/pequod_plus/util.cljc` 的 `consume`（ClojureScript 路径）让每个消费议会面对
`price / num-of-ccs`，聚合时再除以议会数。`consume-process-all-in-db`（SQLite 路径）
直接用全价 `price`，聚合时同样除以议会数。

结果是 SQLite 路径的公共品需求是 ClojureScript 路径的 1/N（N = 30000）。
论文描述的是前者：「We divide the price by the number of consumer councils」。

### 聚合价格增量用带符号均值

`util.cljc` 的 `calculate-price-deltas` 计算 `mean(surplus) / mean(supply, demand)`。
同一类商品内部的正负失衡互相抵消，一百种商品各自失衡 20% 也可能得出接近零的步长，
于是每种商品的调价被压到 0.001 下限。用 `mean(|surplus|)` 更符合意图。

### 污染物开关打开会除零

`src/clj/pequod_plus/populate.clj` 的 `create-ccs-in-csv` 让
`negative_utility_from_exposure` 与 `positive_utility_from_income` 取自同一个列表
`[0.11 … 0.19]`。污染许可公式的指数是 `1/(k−j)`，k 与 j 同分布时除零或符号翻转。

旧版 `ccs.clj` 用的是 `[1.11 … 1.19]`。当前 `csvgen.clj` 把 `include-pollutants?` 写死为
`false`，所以尚未暴露。

## 性能

### `coefficient` 上无索引，但聚合查询按它过滤

`util.cljc` 的 `compute-surpluses-prices-improved` 用
`select sum(quantity) from intermediate_inputs where coefficient = ?` 做聚合，
`nature`、`labor`、`pollutant_demands` 同理。

而 `datasource.clj` 建的索引只有 `wc_id` 与 `intermediate_input_id`。
注意 `intermediate_input_id` 是「该议会的第几个投入槽」，`coefficient` 才是
「这是一百种商品里的哪一种」，两者不是一回事。这四百次查询每轮都是全表扫描。

### 每轮把整个数据集拉进 JVM

`csvgen.clj` 的 `proposal-db` 每轮 `select *` 三张投入表再 `group-by`，
构造几十万个装箱 map 与 keyword。这是 `user` 时间为 `real` 两倍的来源。

### `pe_ifb_compute` 在插入循环内 commit

`src/core.py` 的 `load_data_to_sqlite_db` 在 `while` 循环内部调用 `con.commit()`。
SQLite 的 commit 触发 fsync，实测代价约一千倍，见 [复现记录.md](复现记录.md)。

同一函数把 `split()` 得到的字符串直接插入，所以 `quantity` 列是 TEXT，
`sum(quantity)` 要逐行做字符串到数值的强制转换。

## 已修复项的历史

`get-delta` 第二个参数（「上一轮的价格增量」）在 SQLite 路径上的演变：

| 提交 | 传入值 | 性质 |
|---|---|---|
| `3204491` 之前 | `price` | 传入价格本身（700），使增量恒为上限 0.25，导致震荡 |
| `3204491` Fix oscillating behavior | `pd` | 每种商品各自的增量，步长开始衰减 |
| `44a6d08` Fix extremely slow convergence | 类别聚合值 | 与 ClojureScript 路径一致 |

ClojureScript 路径的对应位置三次提交中未变。所以 `44a6d08` 修的是移植偏差，不是改进算法。
