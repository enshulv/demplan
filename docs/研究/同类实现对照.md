# 同类实现对照

三个做经济计划计算的公开实现，2026-09-05 调研。它们不是本库的上游——本库不从它们取代码，
许可证也不允许（见文末）。调研的目的有两个：确认本库的定位没有被占，
以及把它们当成「同一个 `Economy` 装得下几种机制」这条判据的真实用例。

clone 在 `upstream/socialist_planning/`、`upstream/EPOS/`、`upstream/Economic-Planning/`，
与 `pequod-plus` 同样各带自己的 `.git`，本仓不跟踪。

## 三个对象

| | OLIN-EP | I-EPOS | Economic-Planning |
|---|---|---|---|
| 仓库 | `ssamot/socialist_planning` | `epournaras/EPOS` | `pablovegan/Economic-Planning` |
| 论文 | Samothrakis (2021) | Nardelli 等 (2025) | 无，引 Hagberg 与 Zacharia |
| 形式 | 一次性实验脚本 | Java 框架 | Python 包，有文档与 CI |
| 语言 | Python | Java 8 + Maven | Python + cvxpy |
| 许可证 | GPL-3.0 | GPL-2.0-or-later | GPL-3.0 |
| 最后提交 | 2021-01-10 | 2026-05-22 | 2025-07-07 |
| 粒度 | 部门 | 议会 | 部门 |
| 求解的问题 | 求根 | 组合选择 | 线性规划 |

**没有一个是共用基础设施。** OLIN-EP 的 README 写明它只证可行、不做基准对照；
I-EPOS 的领域是自管理共享经济的通用组合优化，经济计划是它的一个应用；
Economic-Planning 是单机制求解包。本库对标 Concordia 与 AgentSociety 的位置仍然空着。

三个团队各写各的数据模型，谁的经济体都跑不进别人的求解器。这是本库第 7 条要消掉的重复。

### OLIN-EP：非线性投入产出

把配置写成 `(I − F(x))x = d`。`F(x)` 是**产出水平的函数**，也就是投入系数随规模变化，
解法是不动点迭代加非线性最小二乘。论文报告 50,000 中间品、5,000 最终品、200 消费画像，
在一台 i7-8700K 上 20 秒内解完。

计划的好坏按最差的那个消费画像算（原文：the plan is as good as its worst performance）。
这是一个 maximin 目标函数，落在本库 `reference_solution(economy, objective)` 的 `objective` 位上。

### I-EPOS：离散计划的去中心化选择

每个主体手上是**一组有限的候选计划**，从中选一个；全局代价打在聚合信号上；
主体按树形拓扑协调。计划文件的格式是 `cost:values`，一行一个候选。

仓里唯一的数据集是 `gaussian`，即随机生成的向量——**它不带任何经济数据**。
Nardelli 等 (2025) 把它当作 communizing 的技术方案，是机制清单里与 parecon、
Cockshott 并列的一个真实条目。

### Economic-Planning：受约束的线性规划

`cvxpy` 写的多期线性规划，目标是 `minimize Σ c_t · x_t`，`cost_hours` 把工时与进口价加总。
约束包括物料平衡、进出口平衡、跨期劳动力再配置上限（`labor_realloc_constraint`）
与生态上限（`pollutants_constraint`）。多期用滚动时域。
数据是西班牙 INE 与瑞典的供给使用表。

它的 `Economy` 是 pydantic 数据类，每个字段都是**按期一份矩阵的列表**，
`periods` 等于 `len(supply)`。

## 对本库的后果

### 1. 枚举放开有了第一个外部实证需求

`Economy.technology_kind` 现在只认 0 Leontief 与 1 柯布-道格拉斯。OLIN-EP 的 `F(x)` 两个都不是。
一个已发表、有代码、跑到 50,000 中间品的机制，本库的固定层装不下。

「类别属性可声明、枚举放开」这条决策此前只有设计对抗审查的推理支撑，现在有实例。
见 [决策/数据模型.md](../决策/数据模型.md) 2026-09-05。

### 2. 联产品有了第二方证据

Economic-Planning 带 `pollutants_constraint`。排放不是被商品类别集合挡住的，
是被「一单元一产出」挡住——这条此前只有本项目自己的推理。
现在有一个在真实供给使用表上跑的实现把生态上限当成常规约束。

### 3. 闭合经济是第五条没写进清单的假设

Economic-Planning 的 `Economy` 有 `use_import`、`prices_import`、`prices_export`，
`PlannedEconomy` 有 `export_deficit`。本库的 `Economy` 没有任何进出口位置。

世界价格是外生的贸易条件，不是内部出清价，所以补上它不违反「不实现市场机制」。
真正的问题在于：设计对抗审查的 V1 指出参照解声称「Nothing else is imposed」而实际焊了四条假设，
**闭合经济是第四条之外的第五条**，四条里一条都没提到它。

### 4. 判据的用例从三个扩到五个

`spec.md` 原本的判据是 parecon 迭代调价、Cockshott 劳动时间直接计算、
Kantorovich 式线性规划三者跑在同一个 `Economy` 上。三个都是本项目自己设想的。

OLIN-EP 与 Economic-Planning 有代码、有真实数据，比设想的用例硬。
I-EPOS 是 v2 议会粒度的用例：它的主体从**有限候选集里选一个**，
所以 v2 的 `Participant` 接口不能假设提案是连续向量。

### 5. 与上游 2023 年论文列的未来方向重合

Szczepanczyk (2023) 末尾列了七条未来方向，其中「其他生产函数」对上 OLIN-EP 的 `F(x)`，
「环境影响」对上 `pollutants_constraint`。三方各自独立走到同一批缺口上。

## 实测：dep1ex01 上的第一次跨机制对照

问的不是「谁跑得快」，是「同一篮最终消费，两条路各花多少劳动」。
脚本 `.cache/tmp/xmech_probe2.py`，不入库。

经济体：500 商品（五类各 100）、30,000 生产单元、30,000 消费单元、164,742 条投入项。
**全部 30,000 个单元都是柯布-道格拉斯**，一个 Leontief 都没有。

| | 墙钟 | 结果 |
|---|---|---|
| 加载 | 0.78 s | — |
| A 迭代调价（`hahnel_2020_slides`，阈值 5%） | 1.18 s | 14 轮收敛，花劳动 96,415.5 |
| 线性化 | 0.01 s | — |
| B 参照解（`minimize_labor`，下限取 A 交付的那篮消费） | 4.02 s | 最优劳动 53,347.6 |

**A / B = 1.81。**

### 这个数字为什么不能直接引用

三件事让它站不住，而**库现在一件都不说**：

1. **参照解跑不了原始经济体。** `reference_solution` 要求 Leontief，
   而 dep1ex 是 100% 柯布-道格拉斯。要比较就必须先 `linearize`，没有第二条路。
2. **线性化把规模报酬递减换成了不变，而且是静默的。** 实测 dep1ex01 每个单元的
   总弹性（投入指数和加 `effort_c`）落在 0.8136 到 0.9400 之间，中位数 0.8750，
   **30,000 个单元里达到 1 的有零个**。线性化之后 LP 面对的是规模报酬不变的技术，
   于是它高估了扩大规模的收益。**1.81 是真实差距的上界，不是估计值。**
   这就是设计对抗审查 J1 那条的具体后果：它不是抽象的纯度问题，
   它挡住了第一个真实的跨机制对照。
3. **线性化的落点是 A 自己的计划。** B 因此是「在 A 选定的技术上还能省多少」，
   不是「集中式最优」。换一个落点就是另一个数字。

**这三条都要在参照解的结果里说出来。** 现在 `ReferenceResult` 只有 `plan`、
`objective_value`、`status` 三个字段，一个字都没提上面任何一条。
对应设计对抗审查待拍板的那条：给 `ReferenceResult` 加不可关的 `assumptions`，
**从实际构建的程序反读**而不是硬编码。

### 计算效率这一面没有信息量

dep1ex 这个尺度上两条路都是亚秒到数秒级。差别在数量级之内，
而且两边解的根本不是同一类问题（求根 / 组合选择 / 线性规划）。
OLIN-EP 的 50,000 × 5,000 在 20 秒，是一个值得引用的量级靶子，
也支持第 11 条「整个经济体常驻内存」。

**计算效率要到 10⁵ 商品以上才成为问题；经济效率在任何尺度上都是本库真正要回答的那个。**
